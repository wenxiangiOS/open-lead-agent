# open-lead-agent 需求文档

## 1. 文档定位

这份文档是内部需求真相，不是对外 README。

它用来回答：

- 项目为什么要这样设计
- 核心需求有哪些
- 每个需求的关键规则是什么
- 配置入口在哪里
- 实现落在哪些模块
- 当前实现状态如何

如果你只是想使用项目，先看 `docs/getting-started-template.md`。
如果你要写模板配置，先看 `docs/configuration.md`。
如果你要接 API，先看 `docs/integration.md`。

## 2. 项目目标

`open-lead-agent` 要做一个开源、可配置、拟人化、容易上手的 AI 线索收集引擎。

它不是某一个行业的固定机器人，而是一个模板化底座。用户通过配置行业模板，让系统完成：

- 自动开场
- 自然收集资料
- 回答问题和疑虑
- 命中合规边界时停止推进
- 在资料足够后收集联系方式
- 联系方式完成后自然收尾

## 3. 长期原则

1. 足够拟人化：像真人一样接话，不像表单机器人。
2. 开源原则：规则透明、模块清晰、避免把行业逻辑写死在代码里。
3. 可配置：行业差异主要通过模板配置完成。
4. 新用户容易上手：新用户只需要知道行业、字段、联系方式和 FAQ，就能生成可运行模板。

## 4. 对话生命周期

完整对话按业务视角分为：

1. 开场白 Opening
2. 意图理解 Understanding
3. 资料收集 Profile Collection
4. 问题/疑虑 FAQ & Concern
5. 知识库/RAG Knowledge
6. 合规边界 Compliance
7. 联系方式收集 Contact Collection
8. 收尾 Closing
9. 状态记忆 State & Memory

其中 Understanding、State & Memory 是内部支撑模块，新用户通常不用直接配置。

## 7. 关键设计共识

### 7.1 字段分层

字段分为三层：

- `core`：核心字段，主线主动询问，默认有效询问 2 次。
- `medium`：中等字段，可在相关时顺带，默认有效询问 1 次。
- `low`：低优字段，只被动收集，默认有效询问 0 次。

### 7.2 主字段和顺带字段

每轮最多有：

- 1 个主字段 `main_target`
- 0-1 个顺带字段 `side_target`

主字段决定本轮主线。顺带字段只能轻量出现，不能抢主线，也不能让回复变成表单盘问。

### 7.3 有效询问

`ask_limit` 不能理解成“AI 问出口就 +1”。系统应该等用户下一轮回应后，再判断这次是否消耗有效询问次数。

FAQ、顾虑、换话题不消耗当前字段的有效询问次数。

### 7.4 问题/疑虑优先

用户中途问收费、隐私、靠谱不靠谱、为什么问资料时，系统必须先答疑，再决定是否回到资料收集主线。

### 7.5 联系方式后置

联系方式不能过早出现。只有资料达到 `contact.trigger` 条件，或用户主动表达留联系方式意愿时，才进入联系方式收集。

### 7.6 拟人化三要素

拟人化不是多加语气词，而是：

1. 上下文感知
2. 承接式表达
3. 节奏控制

### 7.7 字段权限治理

模型提取出的字段不能直接进入字段接受层。系统需要先根据本轮上下文判断哪些字段允许继续：

- FAQ / 顾虑轮默认不写资料字段。
- 联系方式上下文优先保留联系方式字段。
- 短答优先绑定上一轮实际追问字段。
- 行业专属错槽规则通过模板 `field_permissions.rules` 配置，不写死在引擎里。

### 7.8 字段风险与仲裁

字段通过权限治理后，还要根据 `risk`、`min_confidence`、`write_mode`、来源和历史冲突进入不同提交状态：

- `accepted`：可写入 profile。
- `pending`：需要用户确认，高风险低置信、软确认、历史冲突优先进入这里。
- `provisional`：普通低风险字段低置信时暂存，不污染主档。
- `rejected`：模板外、空值、格式非法或权限拦截。

风险规则必须通用可配置，不能把婚恋字段写死在引擎里。

### 7.9 Dense Intro

用户一轮里同时给出多个资料、需求、联系方式或 FAQ 时，系统要按高信息量输入处理：

- 提示词要求并行提取多字段，不只保留一个字段。
- 语义结果标记 `turn_mode=dense_intro`。
- 记录 `no_reask_fields`，表示本轮已经观察过的字段。
- 仍然必须经过字段权限治理和风险仲裁，不允许跳过安全层。

当前是轻量版，不包含 async backfill。

### 7.10 单轮优先级

用户一轮里可能同时包含资料、联系方式、FAQ、顾虑和需求。系统不能因为字段提取到了很多信息，就直接按字段顺序追问。

需求规则：

- 字段提取和前台回复动作解耦：能提取的字段先进入治理和仲裁，回复动作另行决策。
- 合规边界最优先，由 `CompliancePolicy` 截停。
- 待确认字段优先于 FAQ、联系方式和新字段追问。
- FAQ / 顾虑 / 问题优先于联系方式和资料收集。
- 如果联系方式已满足收尾条件，本轮收尾，不继续追其它联系方式。
- 联系方式收集优先于普通资料收集。
- 普通资料收集是最后的默认动作。

这套规则必须做成公共模块，不能只服务婚恋模板。行业差异通过 FAQ、RAG、字段配置、联系方式配置和合规配置表达。
