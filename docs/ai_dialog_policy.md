# AI 对话策略方案

## 一、方案目标

### 1.1 目标定义

这套方案的目标不是单纯“把字段问全”，而是同时满足 4 个要求：

| 目标 | 说明 |
|---|---|
| 可实行 | 规则明确，能直接拆成代码逻辑 |
| 能落地 | 不依赖过度理想化判断，不引入失控复杂度 |
| 更拟人化 | 不再像流程机，能承接、转场、顺着用户聊 |
| 收集效率不丢失 | 核心字段仍然要稳定推进 |

### 1.2 设计原则

- 保留字段分级
- 保留优先顺序，不用固定死顺序
- 保留每轮 `1主 + 1顺带`
- 联系方式继续走现有专门逻辑
- 不再扩张复杂状态机
- 增加“拟人化表达层”，但规则必须能实现、能测试

### 1.3 本项目对“拟人化”的统一定义（新增）

后续凡是讨论“提高拟人化程度”，统一按以下口径理解，不按“更会说话/更可爱/更口语化”来理解：

- AI 要先像是在听人说话
- AI 要先接住用户刚表达的重点，而不是立刻切到脚本字段
- AI 要像真人一样，自然而然承接用户当前这句话往下聊
- 拟人化的核心标准是“听懂了，并且顺着接上了”
- 单纯增加语气词、口头禅、表情、温柔措辞，不等于拟人化提升
- 如果回复只是取字段、换字段、推进流程，即使语气柔和，也不算高拟人化

评审和优化时，优先检查：

- 有没有接住用户刚说的重点
- 有没有顺着用户当前话题自然推进
- 有没有机械切字段、像问卷
- 有没有只是在取信息，而不是在对话

### 1.4 “像人在接话”专项回归命令（新增）

如果要单独回归“AI 是否像在听人说话、并自然承接用户当前这句话”，优先跑下面这条命令：

```bash
python3 scripts/run_random_user_simulation.py \
  --cover-scenarios \
  --seed 42 \
  --verbose \
  --listener-first-suite
```

这条命令只跑“像人在接话”相关专项场景，覆盖：

- 偏好承接
- FAQ 咨询承接
- 边界/顾虑承接
- 吐槽/反感承接
- 澄清类承接
- 换话题承接
- 资料 + FAQ / 边界 / 顾虑 的混合输入承接

使用建议：

- 日常改 prompt、快路径回复、FAQ 承接后，先跑这条专项命令
- 准备发版或做全量回归时，再跑完整的 `--cover-scenarios`

## 二、字段分级总览

### 2.1 字段分类

| 级别 | 字段 | 收集策略 | 主动询问上限 | 不答处理 |
|---|---|---|---:|---|
| 核心字段 | 性别、年龄、学历、职业、工作地 | 优先主线覆盖 | 2次 | 达上限后视为“已覆盖完成”，不再硬追问 |
| 准核心 | 婚况 | 至少覆盖1次 | 1次 | 问过1次或成功收集后，视为“已覆盖完成” |
| 中等字段 | 月薪、择偶要求 | 自然穿插收集 | 1次 | 问过1次或成功收集后，视为“已覆盖完成” |
| 后置核心 | 联系方式 | 独立进入条件 | 独立策略 | 不再由“字段是否收集成功”直接决定进入时机 |
| 低优字段 | 身高、姓名、体重 | 永不主动问 | 0次 | 用户主动说才记录 |

补充口径：

- 上面的“2次 / 1次”都是硬上限，不因用户类型、用户配合度、场景切换而改变。
- “主动询问上限”表示最多可主动尝试的次数，不表示必须问满该次数。
- 用户第一次就答清楚时，立即停止该字段主动追问。
- 本项目后续统一使用“覆盖完成”而不是“收集成功”来判断资料主线是否可以往下走。

### 2.2 各字段详细规则

| 字段 | 级别 | 主动询问上限 | AI 指令要点 |
|---|---|---:|---|
| 性别 | 核心 | 2次 | 前两轮优先确认；第2次可解释用途 |
| 年龄 | 核心 | 2次 | 第2次可接受模糊值 |
| 学历 | 核心 | 2次 | 第2次可解释匹配用途 |
| 职业 | 核心 | 2次 | 第2次可表示“多了解你一点” |
| 工作地 | 核心 | 2次 | 第2次接受模糊地区 |
| 联系方式 | 后置核心 | 独立策略 | 只在上游 gate 通过后进入电话/微信逻辑 |
| 婚况 | 准核心 | 1次 | 柔性确认，不像审查；问过1次或收集成功即算已覆盖 |
| 月薪 | 中等 | 1次 | 必须带“不方便说也没关系”；问过1次或收集成功即算已覆盖 |
| 择偶要求 | 中等 | 1次主动+持续被动提取 | 平时优先穿插问；问过1次或收集成功即算已覆盖 |
| 身高 | 低优 | 0次 | 永不主动问 |
| 姓名 | 低优 | 0次 | 永不主动问 |
| 体重 | 低优 | 0次 | 永不主动问 |

## 三、收集顺序与调度规则

### 3.1 优先顺序

不是固定死顺序，而是优先顺序。

第一优先：基础核心主线
- 性别
- 年龄
- 工作地

第二优先：核心补全主线
- 学历
- 职业

第三优先：收尾前自然穿插
- 婚况
- 择偶要求
- 月薪

第四优先：后置核心
- 联系方式

说明：

- 这只是收集顺序，不改变字段分类。
- 核心字段是主任务，准核心和中等字段只是锦上添花，不能影响核心字段收集成功率。
- 联系方式虽然仍然是核心字段，但明显后置，不进入首段主线。
- 婚况、择偶要求、月薪允许在核心字段推进过程中自然穿插，但不能抢核心主线。
- 首段不以“收齐全部9个字段”为目标，而是优先推进核心字段。

被动收集：
- 身高
- 姓名
- 体重

### 3.2 每轮调度规则

| 规则项 | 调度规则 |
|---|---|
| 主目标字段 | 每轮只推进1个主目标字段 |
| 顺带补充字段 | 每轮最多顺带1个相关字段 |
| 已知字段 | 已提取到的字段不再重复问 |
| 连续追问限制 | 同一字段不能连续两轮都问 |
| 用户疑问 | 先回答疑问，再回主线 |
| 低优字段 | 不允许主动打断主线去问 |

补充调度要求：

- 首段默认不追求把核心、准核心、中等字段全部轮完。
- 达到以下任一条件时，应停止主动收集，转自然聊天或答疑：
  - 已拿到大部分基础核心字段，足够支撑后续自然聊天
  - 用户已经开始主动展开补充信息
  - 用户出现困惑、敷衍、不耐烦、连续低信息回复
  - 当前会话主动问题轮次已经偏长
- 核心字段即使允许最多2次主动尝试，也不能为了“凑满2次”重复追问。
- 准核心字段 `marital_status` 最多主动问1次，一次未拿到即转被动提取。
- 中等字段主动问过1次后，后续只能被动提取，所有 fallback / interleaving / bridge-back 都必须遵守该限制。
- 准核心和中等字段不能打断核心字段主线，也不能抢在核心字段之前成为默认主目标。
- `partner_requirement` 平时仍按“顺带穿插”处理；但当核心字段都已覆盖、联系方式又被它卡住时，可临时升级为兜底主目标问1次。

### 3.3 准核心与中等字段穿插时机

| 触发场景 | 穿插字段 | AI 指令 |
|---|---|---|
| 年龄已确认后 | 婚况 | 仅在感情/关系语境自然带出，一次未拿到即跳过 |
| 年龄或工作地已确认后 | 择偶要求 | 自然问对另一半要求，不强求完整 |
| 职业已确认且节奏稳定 | 月薪 | 轻问收入，并明确“不方便说也没关系” |
| 用户主动提及收入待遇 | 月薪 | 顺势确认模糊收入范围 |

穿插原则：

- 核心字段仍然是主线，`marital_status`、`partner_requirement`、`monthly_income` 只能顺带出现。
- 默认每轮 1 个主目标字段；准核心/中等字段只允许作为自然补充，不允许连续多轮抢主线。
- `partner_requirement` 最适合穿插，`marital_status` 次之，`monthly_income` 最谨慎。
- 如果用户当前回答很短、很冷、很敷衍，则本轮不再顺带穿插第二个问题。

## 三点五、联系方式进入 Gate（新增）

联系方式进入不再用“字段是否收集成功”单一判断，而是统一经过 4 个 gate：

### 3.5.1 Coverage Gate

- 核心字段 `sex/age/education/occupation/location`
  - 收集成功，或
  - 已主动问满 2 次
  - 满足其一即视为“已覆盖完成”
- 准核心/中等字段 `marital_status/partner_requirement/monthly_income`
  - 收集成功，或
  - 已主动问过 1 次
  - 满足其一即视为“已覆盖完成”
- 只有当上述字段全部“已覆盖完成”，才有资格进入联系方式判断

### 3.5.2 Profile Sufficiency Gate

- 即使 Coverage Gate 已通过，也不代表立刻可进联系方式
- 仍要求核心字段成功收集数达到最低门槛，当前统一口径为：
  - `sex/age/education/occupation/location` 中，至少成功收集 3 个
- 如果 Coverage Gate 通过但核心成功数不足 3：
  - 不进入联系方式
  - 不再机械逐字段追问
  - 转入“开放式补画像”

### 3.5.3 Turn Quality Gate

- Coverage 和画像都足够时，仍需看当前轮是否适合切联系方式
- 以下轮次通常不切联系方式：
  - 用户在提问或表达顾虑
  - 用户处于投诉修复 / 边界收口
  - 当前轮只适合轻承接

### 3.5.4 Cost Control Gate

- 如果用户连续不配合、连续跑题、开放式补画像多次失败，或会话成本已偏高：
  - 不再继续高压推进资料或联系方式
  - 转入低压轻聊或礼貌收口

### 3.5.5 最终进入条件

只有同时满足下面 4 条，才允许真正进入联系方式：

- Coverage Gate = 通过
- Profile Sufficiency Gate = 通过
- Turn Quality Gate = 通过
- Cost Control Gate 允许继续推进（`full` / `compact`）

## 三点六、状态机收敛（新增）

当前资料收集主线只需要记住 6 个策略状态：

- `collect_core`：核心字段仍有未覆盖项
- `collect_medium`：核心已覆盖，中等字段仍有未覆盖项
- `open_profile_repair`：字段已覆盖，但画像不足，改用开放式补画像
- `contact_flow`：允许进入联系方式逻辑
- `low_pressure_chat`：停止主动推进，只轻承接或短答
- `terminate_conversion`：停止主流程，礼貌收口

## 四、拟人化增强层

### 4.0 首轮体验总原则（新增）

首轮用户体验优先级：

`接住用户 > 建立信任 > 给用户选择感 > 再推进字段`

首轮明确要求：
- 用户第一句是纯问候（如“你好”“在吗”“hi”）时，必须先做自然承接，不得直接抛字段问题
- 不允许因为“已写入 sex/已有默认资料”就跳过问候承接
- 首轮可推进字段，但必须是“承接后轻推进”，不能表单式直问

### 4.1 承接规则

每次提问前，优先做承接，不要直接硬问。

承接顺序：
1. 承接用户情绪
2. 承接用户内容
3. 给一句轻反馈
4. 再推进主目标字段

示例逻辑：
- 用户积极回答：轻反馈后继续推进
- 用户犹豫：先安抚，再降低问题压力
- 用户开玩笑：可轻接一句，再回主线
- 用户敷衍：不要立刻压问，先换轻方式
- 用户防备：先解释用途，再决定是否继续问

### 4.2 转场规则

从一个字段切到另一个字段时，必须经过转场。

标准转场结构：
`承接上一句 → 反馈/认可 → 进入下一字段`

禁止：
- 刚问完职业，下一句直接问收入
- 刚问完年龄，下一句直接问婚况且无过渡

### 4.2.1 禁止开场白规则修订（新增）

“禁止开场白”只表示：
- 禁止重复系统欢迎语
- 禁止重复“自我介绍型”固定开场

不表示：
- 禁止短承接（如“在的呀～”）
- 禁止一句轻反馈后再推进字段

执行口径：
- 非首轮：禁止重复欢迎语，但允许 1 句承接 + 1 个轻问题
- 首轮纯问候：必须先承接，再推进

### 4.3 非收集型互动规则

为了更像真人，允许少量非收集型互动。

规则：
- 每收集 2 到 3 个有效字段，可插入 1 轮轻互动
- 轻互动只做短反馈，不长聊
- 下一轮必须回到主线

可做：
- 简短认可
- 轻微共情
- 对择偶表达做一句自然反馈

不可做：
- 连续两轮不收集
- 输出大段建议
- 变成陪聊

### 4.3.1 用户控制权规则（新增）

首轮或关键转场轮，允许给用户一个轻量选择：
- “我先快速了解你两三点” 或 “你先说你最在意的”

规则：
- 仅提供 2 个短选项，不做复杂分支问卷
- 选项文案必须口语化、低压力
- 用户未选择时，默认走“先听用户说，再轻推进”

### 4.4 用户类型适配

| 用户类型 | 特征 | 对应策略 |
|---|---|---|
| 配合型 | 回答直接，信息量高 | 推进稍快，允许1主+1顺带 |
| 保守型 | 回答短，对敏感问题回避 | 多解释、少压迫、少追问 |
| 敷衍型 | “嗯”“还行”“再说吧”较多 | 放慢推进，更多被动提取 |
| 话题型 | 愿意展开讲要求、生活、经历 | 先顺着聊，再从中提取字段 |

### 4.5 记忆回用规则

这是拟人化提升最大的新增点之一。

规则：
- 用户已经说过的信息，后续回复里要自然回用
- 回用要短，不要像复读资料
- 回用的目的是让用户感到“被听见了”

允许的回用：
- 地区
- 职业
- 择偶要求
- 已表达的偏好
- 已表达的顾虑

示例：
- “你刚刚说更看重成熟稳重，这个我记住啦”
- “你在杭州的话，同城筛选会更方便一点”

禁止：
- 大段重复用户资料

## 五、拟人化与业务边界口径（新增）

### 5.1 本轮优化结论

本项目后续讨论“提高拟人化”，统一理解为：

- 更像真人在接话，不像在执行脚本
- 更像顺着用户聊天，不像在填表
- 更像在轻推进，不像在硬销售

不把“更会说话”“更热情”“更像红娘销售”当成拟人化目标。

### 5.2 这轮从真实聊天中提炼出的可学习精华

可直接学习并固化到 prompt / 规则 / 回归里的，是以下能力：

- 先回应用户当前这句话，再推进下一步
- 一次只推进一个核心点，避免连珠炮提问
- 提问前给一句轻量由头，让问题更自然
- 多用短句和自然停顿，少用公告式长句
- 用户只回“嗯/好/好的/行/可以”时，也要顺着推进一小步
- 适度给用户退路，例如“你方便的话”“先聊聊也行”“不急”
- 常见 FAQ 先解释清楚，再决定是否回主线
- 联系方式转场要轻，不要像销售 closing

### 5.3 明确不能学习的内容

以下内容即使在线下人工话术中存在，也不能直接让 AI 学：

- “给你发资料”
- “把谁的资料推给你”
- “我推荐给他/她”
- “介绍某个男生/女生的具体情况”
- “互换照片/互换联系方式”
- “安排见面/安排线下”
- “发具体定位/具体地址”
- “第一时间联系你”
- “1到8小时 / 1到2天 / 24到48小时内联系你”

原因不是“不自然”，而是这些表达会制造当前系统承接不住的明确业务预期。

### 5.4 推荐表达方向

联系方式用途：

- 推荐说法：后面沟通更方便、方便后续同事了解情况、后续确认会更顺一点
- 禁止说法：有合适的人选时第一时间联系你、通知你、给你发资料

门店/线下：

- 推荐说法：深圳有线下门店，具体怎么安排以后续沟通为准
- 禁止说法：匹配后给你发具体定位、安排线下见面

照片/资料：

- 推荐说法：这类内容不是当前阶段直接发的，会先看沟通和隐私边界
- 禁止说法：双方合适后互换照片、先把资料发你

流程/匹配：

- 推荐说法：先了解基本情况和偏好，后面再继续沟通
- 禁止说法：马上推进见面、马上安排、快速出结果

### 5.5 低信息回复专项要求

用户若只回以下低信息表达：

- 好
- 好的
- 嗯
- 行
- 可以
- 回头再说

执行口径：

- 不要误判为用户已提供联系方式
- 不要机械复读上一轮问题
- 电话推进过一次后，低信息确认可自然切到微信方案
- 双渠道都推进过后，低信息确认应暂停联系方式推进
- “回头再说”优先按边界/暂缓处理，不再继续硬推联系方式

### 5.6 FAQ 统一边界

以下 FAQ 场景统一按“先解释，再保持边界”处理：

- 收费
- 门店
- 怎么匹配
- 为什么要留电话/微信
- 能不能直接加对方
- 能不能先看照片
- 多久能安排 / 多久能找到
- 平台靠不靠谱 / 安不安全

统一要求：

- 可以解释，但不要讲成承诺
- 可以自然，但不要讲成营销
- 可以保留真人口语感，但不要说满
- FAQ 轮不要顺手切回资料收集

新增可落地情绪标签：

| 情绪标签 | 识别信号 | 处理方式 |

## 五、字段问法层级

### 5.1 第一次提问

原则：
- 轻
- 短
- 顺着话题
- 不解释过多

适用：
- 用户配合
- 前几轮
- 不太敏感的字段

### 5.2 第二次追问

原则：
- 必须换问法
- 先承接
- 可解释用途
- 可降低回答门槛

适用：
- 核心字段
- 婚况
- 用户第一次回避但未明确拒绝

### 5.3 敏感字段问法层级

| 问法层级 | 使用场景 |
|---|---|
| 直接轻问 | 用户配合度高时 |
| 柔和确认 | 用户稍保守时 |
| 带解释轻问 | 第2次追问或用户表达顾虑时 |
| 降门槛问法 | 接受模糊回答时 |

### 5.4 婚况问法分层

| 问法类型 | 使用场景 |
|---|---|
| 自然带出型 | 聊到找对象、感情状态时 |
| 轻确认型 | 已聊到部分背景信息后 |
| 缓冲解释型 | 用户谨慎或第一次没答 |

### 5.5 择偶要求问法分层

| 问法类型 | 使用场景 |
|---|---|
| 开放型 | 用户愿意表达时 |
| 轻提示型 | 用户表达少时 |
| 延展型 | 用户已经说出一点偏好时 |

## 六、字段状态管理

### 6.1 推荐实现状态

为了可落地，不建议保留过多复杂状态。实现层建议只用 5 种：

| 状态 | 含义 |
|---|---|
| unasked | 未主动问过 |
| asked_once | 已问1次未收集到 |
| asked_twice | 已问2次未收集到 |
| collected | 已收集到 |
| skipped | 达上限或明确不答 |

### 6.2 实现建议

- `passive_collected` 不单独存状态，直接算 `collected`
- `rejected / deferred` 不单独做主状态，可记在日志或上下文原因里
- 这样更利于实现和调试

## 七、智能提取策略

### 7.1 核心原则

从每条用户消息中，尝试提取所有可能字段，不局限于当前主目标字段。

### 7.2 提取范围

- 核心字段：性别、年龄、学历、职业、工作地、联系方式
- 准核心字段：婚况
- 中等字段：月薪、择偶要求
- 低优字段：身高、姓名、体重

### 7.3 提取规则

- 当前没在问，也要提取
- 一句话多个字段，一次性全部提取
- 后续更清晰值可覆盖模糊值
- 模糊值允许归一化存储
- 低优字段只提取，不反向触发追问
- 用户情绪和配合度也要同步更新为对话标签

## 八、联系方式触发规则

### 8.1 进入联系方式逻辑的时机

| 触发条件 | 是否进入 |
|---|---|
| 已拿到4个及以上核心/准核心字段 | 是 |
| 已拿到年龄+工作地+职业/学历之一+婚况 | 是 |
| 只拿到1-2个基础字段 | 否，继续完善画像 |
| 用户主动提出愿意留联系方式 | 是，可提前进入 |

### 8.2 边界说明

- 联系方式怎么问，不改你现有策略
- 这套方案只控制“何时进入”
- 进入联系方式阶段时，仍允许被动收集其它字段
- 不要在资料基础太薄时过早切入联系方式

## 九、用户疑问处理

### 9.1 优先原则

用户疑问 > 字段收集

流程：
- 检测疑问
- 暂停收集
- 回答疑问
- 简短确认是否还有问题
- 回到原主目标字段

### 9.2 疑问类型

- 收费
- 隐私
- 信任
- 用途

### 9.3 回答要求

- 先回应顾虑
- 再解释
- 语气像真人客服/红娘
- 回答后不要突然跳到无关字段

## 十、性能与拟人化耦合约束（新增）

### 10.1 首轮延迟阈值

- 首轮目标：P95 < 3 秒
- 超过 3 秒时：先返回短承接句，再继续生成完整推进句（或下一轮补齐）

### 10.2 慢响应兜底话术

当模型慢或波动时，优先返回短句维持“人在对话”的感受，例如：
- “在的呀，我先看下你的情况～”
- “收到，我帮你理一下，马上给你建议”

### 10.3 体验底线

- 任何情况下不允许“长时间等待后直接抛字段问题”
- 性能降级时优先保留承接感，其次才是字段推进速度

### 10.4 打招呼混合策略（新增）

为平衡拟人感与成本，打招呼不走“全量 AI”或“全量模板”，采用混合路由：

- 首轮纯问候：优先走轻量模板承接，不直接上重模型
- 非首轮纯问候：按概率进入 AI，剩余走轻量承接
- 用户消息含实质内容（非纯寒暄）：直接走正常 AI 主流程

推荐默认参数：

- `MQ_FOLLOWUP_GREETING_AI_PROB=0.30`
- `MQ_GREETING_FIRST_TURN_DELAY_MIN=0.8`
- `MQ_GREETING_FIRST_TURN_DELAY_MAX=2.2`
- `MQ_GREETING_FOLLOWUP_DELAY_MIN=0.9`
- `MQ_GREETING_FOLLOWUP_DELAY_MAX=2.6`

约束：

- 打招呼快捷路径也要加随机延迟，避免机械秒回
- 不允许固定时延，必须有抖动

## 十一、收尾与异常处理

### 11.1 收尾条件

| 收尾类型 | 触发条件 |
|---|---|
| 标准完成 | 联系方式完成 + 至少4个核心/准核心真实值 |
| 可接受完成 | 联系方式完成 + 至少3个核心/准核心真实值 |
| 提前收尾 | 用户明显不愿继续 / 双拒联系方式 / 持续低信息 |

### 11.2 异常情况处理

| 异常情况 | 处理指令 |
|---|---|
| 核心字段未答1次 | 后续换方式再问1次 |
| 核心字段未答2次 | 标记 skipped，继续下一个字段 |
| 准核心字段未答2次 | 先跳过，后续如用户主动提到再补收 |
| 中等字段未答 | 不追问，转回主线 |
| 用户中途离开 | 保存断点，下次从未完成主目标继续 |
| 用户连续低信息回复 | 放慢节奏，优先承接，必要时提前收尾 |
| 用户主动跳话题 | 先承接，再提取字段，随后回主线 |

补充约束：

- 高风险提前收尾场景，例如年龄限制、已婚、分居、离异手续未办妥、LGBT，不默认切到 AI 自由生成。
- 这类场景优先使用多变体预设话术，既保持合规和稳定，也尽量降低固定模板的机械感。

## 十二、技术落地建议

### 12.1 实现拆分

建议拆成 4 层：

| 模块 | 职责 |
|---|---|
| 字段调度层 | 决定当前主目标字段和顺带字段 |
| 提取层 | 从用户消息中提取全部字段 |
| 表达层 | 负责承接、转场、问法层级 |
| 联系方式层 | 继续使用现有独立逻辑 |

### 12.2 最小实现顺序

1. 先做字段优先级调度
2. 再做婚况提升和中等字段穿插
3. 再做承接/转场模板
4. 再做用户类型适配
5. 最后做记忆回用增强

这样最稳。

- 已把资料成熟度判断从旧的固定字段链路改为“可服务画像阈值”

### 12.4 Prompt 落地与拟人化优化

`src/services/prompts.py` 已按这套方案做过多轮收敛，当前已完成的重点包括：

- 主提示词已切到“核心 / 准核心 / 中等 / 低优”四层策略
- 已加入当前主目标字段、顺带字段、用户类型、联系方式可进入状态
- 已限制每轮 `1主 + 1顺带`，避免连珠炮提问
- 已明确低优字段只被动提取，不主动追问
- 已增加联系方式主目标锁定，避免进入联系方式后又被月薪、低优字段打断
- 已降低模板味：减少机械“小哥哥/小姐姐”、过度语气词、夸张吹捧和营销式开场
- 已收紧离异确认、分居结束、二次追问示例，使表达更自然但不破坏业务刚性

### 12.5 当前已验证的行为结论

基于真实 AI 回归，当前这套实现已经验证过以下关键行为：

- 资料未成熟时，不会主动追问身高、体重、姓名
- 用户先提问时，会先答疑，再回主线
- 资料成熟后，才进入联系方式
- 用户主动给出多个字段时，不会回头逐项重复盘问
- 用户分居中时，会礼貌结束，不继续推进
- 用户双拒联系方式时，会走到收尾，不会无限纠缠
- 用户只留微信时，不会卡死在联系方式阶段
- 离异手续办妥后，会继续回主线，而不是误结束

## 十四、最终结论

| 维度 | 最终规则 |
|---|---|
| 核心字段 | 性别(2次)、年龄(2次)、学历(2次)、职业(2次)、工作地(2次)、联系方式(独立逻辑) |
| 准核心 | 婚况(1次，柔性确认，未拿到即转被动提取) |
| 中等字段 | 月薪(1次)、择偶要求(1次主动+持续被动提取) |
| 低优字段 | 身高、姓名、体重，不主动问，只智能提取 |
| 收集顺序 | 优先顺序：性别/年龄/工作地 → 学历/职业 → 婚况/择偶要求/月薪自然穿插 → 联系方式 |
| 首段目标 | 首段优先推进核心字段，不以收齐全部9个字段为目标 |
| 次数口径 | 核心最多2次，婚况最多1次，中等字段最多1次；这些都是硬上限，但不是必须问满 |
| 调度规则 | 每轮1个主目标，最多1个顺带字段 |
| 拟人化增强 | 承接、转场、完整问句、少机械确认、少策略腔、情绪识别 |
| 联系方式 | 沿用现有逻辑，只增加进入时机控制 |
| 状态实现 | 推荐5状态实现，避免过度复杂 |
| 落地方式 | 先改调度，再改表达层，再补测试 |
