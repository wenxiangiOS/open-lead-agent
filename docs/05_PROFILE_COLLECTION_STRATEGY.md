# 资料收集与 AI 对话统一策略最终方案

## 1. 文档定位

本文档是当前项目中资料收集主流程、AI 对话承接、联系方式切入、成本控制与边界处理的唯一主文档。

后续涉及以下内容时，统一以本文档为准：

- 资料收集字段分层
- 主流程状态机与 `next_mode`
- 进入联系方式的条件
- 用户提问/顾虑时的优先级处理
- 错位回答、回避回答、补问规则
- 联系方式流开始后的冻结规则
- “无有效推进”的统一定义
- 对话承接、转场、FAQ 边界与拟人化口径

## 2. 方案目标

在不改现有统一 prompt 结构的前提下，只优化策略层，解决以下问题：

1. 不再把“收集成功”误当成“流程完成”。
2. 不再因为 `partner_requirement` 之类字段卡死在联系方式前。
3. 不会在画像太空时硬切联系方式。
4. 不会在没有下一步目标时空收尾。
5. 不会被不配合用户持续消耗 token。
6. 用户在字段收集中途提问、表达顾虑或质疑时，系统先答疑，再恢复主流程。
7. 联系方式流开始后，主资料流冻结。
8. 对“无有效推进”给出统一定义，稳定成本控制。
9. 保持对话像真人接话，而不是像填表或跑脚本。

## 3. 范围与非目标

本方案只改策略层，不改：

- 统一 prompt 结构
- AI 的人格与总体表达风格
- 中等字段穿插式收集的产品要求
- 联系方式内部的电话/微信细分流程

本方案当前明确不做：

- 字段敏感度分层
- 恢复目标的多轮有效期机制
- 开放式补画像的目标字段记录
- 额外扩张新的复杂状态机

这些都可以作为后续迭代，但不属于当前版本的必须项。

## 4. 统一术语

### 4.1 收集成功

指某个字段已经拿到可落档值。

### 4.2 覆盖完成

指某个字段虽然不一定收集成功，但已经达到本项目允许的主动推进上限，因此主流程不再依赖它继续机械追问。

### 4.3 有效覆盖尝试

指一次真正成立的字段推进尝试。只有这类尝试才计入 `ask_count`。

### 4.4 无有效推进

指本轮既没有推进字段、也没有推进联系方式、也没有解除用户顾虑。

### 4.5 主目标字段 `main_target`

指本轮最优先推进的字段。每轮只能有一个。

### 4.6 顺带字段 `side_target`

指本轮允许自然顺带带出的字段。可以没有，但不能抢主线。

### 4.7 兜底字段 `forced_cover_target`

指平时不抢主线，但在流程被阻塞时临时升级为必须覆盖一次的字段。

## 5. 拟人化的统一定义

本项目后续凡是讨论“提高拟人化程度”，统一按以下口径理解：

- AI 要先像是在听人说话。
- AI 要先接住用户刚表达的重点，而不是立刻切字段。
- AI 要像真人一样顺着用户当前这句话自然往下聊。
- 拟人化的核心标准是“听懂了，并且顺着接上了”。
- 单纯增加语气词、口头禅、表情、温柔措辞，不等于拟人化提升。
- 如果回复只是取字段、换字段、推进流程，即使语气柔和，也不算高拟人化。

评审时优先检查：

- 有没有接住用户刚说的重点
- 有没有顺着当前话题自然推进
- 有没有机械切字段、像问卷
- 有没有只是在取信息，而不是在对话

## 6. 字段分层

### 6.1 核心字段

- `sex`
- `age`
- `education`
- `occupation`
- `location`

### 6.2 中等字段

- `marital_status`
- `partner_requirement`
- `monthly_income`

补充说明：

- `monthly_income` 在字段名上保留不变，但策略语义统一按“收入信息字段”处理。
- 该字段允许收集：
  - 月薪
  - 年薪
  - 收入区间
  - 大概收入水平

### 6.3 联系方式字段

- `phone`
- `wechat`

注意：

- 联系方式不参与核心/中等字段覆盖完成判断。
- 身高、姓名、体重等低优字段仍只做被动提取，不主动追问。

## 7. 字段收集总原则

### 7.0 AI-first 提交契约

从本版本开始，资料收集主链新增以下硬约束：

- 如果统一理解链中的 AI 已明确识别出：
  - 哪些是用户自己的信息
  - 哪些是择偶要求
  - 每个字段的值是什么
  - 并给出 `direct_write`
  那么该字段必须直接进入收集链，不允许后链路再做第二次语义改判。

唯一允许阻止主档写入的原因：

- 字段值格式非法
- 和已有稳定值冲突
- CAS 并发保护失败
- AI 自己标记为 `soft_confirm`

规则层职责边界（新增硬约束）：

- 规则层只负责格式校验、冲突校验、安全边界，不负责二次改写字段语义。
- 非联系方式字段中，regex / 词库 / guard 只能做补充判定，不能覆盖 AI 已 `committed` 的语义归属。
- 联系方式字段允许严格规则校验（如手机号、微信号格式），但不得反向影响已提交的非联系方式字段。

明确禁止：

- 因为后置 regex/guard 觉得像择偶要求，就把 AI 已识别的本人字段改掉
- 因为 pre-generation backfill、contextual short reply backfill、legacy extraction 重新判语义，导致字段消失
- 因为高风险阈值策略重复评估，把已进入 `accepted(committed)` 的 AI 字段重新降级

### 7.1 主线原则

- 核心字段是主线。
- 中等字段继续保留穿插问、自然结合问的产品要求。
- 联系方式明显后置，只有上游 gate 全部满足才允许进入。

### 7.2 每轮调度原则

- 每轮只允许一个 `main_target`。
- 每轮最多一个 `side_target`。
- 已收集字段不再主动重复问。
- 当前轮如果用户在提问、表达顾虑、投诉，则先答疑，不推进主目标。

### 7.3 交互原则

- 能承接就先承接，再推进。
- 能自然带出就自然带出，不做表单式连珠炮。
- 能轻问就不重问。
- 能顺带就不硬切。

### 7.4 核心字段顺序原则

核心字段仍然有主骨架，但不要求永远固定死序。

稳定要求：

- `sex` 仍然优先，通常作为最前面的核心字段。
- `age / location / education / occupation` 仍然属于核心主线。
- 不允许在核心字段明显未完成时，直接跳去中等字段或联系方式。

本版本新增规则：

- `age / location / education / occupation` 允许“受控扰动”式轻微换位。
- 这里的“受控扰动”不是完全随机，而是在有限候选本科顺序里做稳定选择。
- 目标是降低表单感，让对话更像顺着聊，而不是每次都固定成同一条采集路径。

因此，系统允许出现下面这类差异：

- 有的会话在 `sex` 后先问 `age`
- 有的会话在 `sex` 后先问 `location`
- 有的会话在 `sex` 后先问 `education`

但以下边界不变：

- `sex` 不应该长期被拖到很后面
- 未完成核心字段时，不能因为顺序变化而越过 Coverage Gate
- 顺序变化不改变“核心字段成功或问满 2 次算覆盖”的规则
- 顺序变化不改变联系方式进入条件

### 7.5 首轮分流原则

首轮不再统一按“直接开始问核心字段”处理，而是先判断用户首句属于哪一类入口。

当前统一分成 7 类：

1. 纯打招呼 / 试探在线
2. 首轮疑似错字 / 乱码 / 无法稳定理解
3. 明确表达求偶意图
4. 首轮主动提供资料
5. 首轮先问 FAQ / 可信度 / 收费 / 门店
6. 边界 / 拒绝型开场
7. 混合型首轮

具体口径如下：

- 纯打招呼：
  - 先建立连接，不直接采集资料
  - 轻问来意，确认用户是想找对象还是先了解情况
- 首轮疑似错字 / 乱码 / 无法稳定理解：
  - 进入 `opening_clarify`
  - 先轻量承认“这句没完全看懂/没太接住”
  - 再把对话拉回低压来意确认，如“想找对象 / 先了解下”
  - 不允许这一轮直接切 `sex / age / location` 等字段采集
- 明确表达求偶意图：
  - 不重复确认“是不是要找对象”
  - 直接承接后进入主线资料收集
- 首轮主动提供资料：
  - 先接住并入档用户已给的信息
  - 不回到机械固定顺序
  - 从相邻字段继续推进
- FAQ / 可信度 / 收费 / 门店：
  - 本轮先答疑，不采集资料
  - 下一轮再视用户态度回主线
- 边界 / 拒绝型开场：
  - 先接住边界
  - 不争辩，不立刻追问
  - 轻量降压后再看是否继续
- 混合型首轮：
  - 先识别主问题
  - FAQ / 顾虑优先答
  - 已给资料同步入档
  - 下一步按主线或相邻字段继续

混合型首轮的优先级建议：

1. 风险 / 顾虑
2. 明确提问
3. 明确求偶意图
4. 已给资料
5. 纯打招呼

### 7.6 开场连接型消息原则

本项目里，“打招呼”不再只理解为单个关键词，而是统一归入 `opening_connective`。

`opening_connective` 至少包含 4 类：

1. 普通打招呼
2. 连接试探
3. 组合型打招呼
4. 轻咨询开场

典型示例：

- 普通打招呼：
  - `你好`
  - `您好`
  - `哈喽`
  - `嗨`
  - `hi`
  - `hello`
- 连接试探：
  - `在吗`
  - `在不在`
  - `有人吗`
  - `有人在吗`
  - `方便聊吗`
  - `有空吗`
  - `可以聊吗`
- 组合型打招呼：
  - `你好，在吗`
  - `你好呀，在吗`
  - `hi，在吗`
  - `你好还在吗`
  - `在吗在吗`
  - `hello你好`
- 轻咨询开场：
  - `想了解下`
  - `想了解一下`
  - `看看情况`
  - `先咨询下`
  - `想问一下`

统一处理规则：

- 只要首轮整体仍是在建立连接，而不是明确求偶意图、FAQ、主动给资料或边界表达，就进入 `opening_probe`
- `opening_probe` 的回复必须先连接，再探测来意
- 不允许因为是组合句、重复句或中英混合，就误掉回字段采集

禁止行为：

- 用户说 `你好，在吗` 时直接问 `sex`
- 用户说 `hi` 时直接切核心字段
- 用户说 `想了解下` 时直接开始采集资料
- 用户首轮输入明显无法稳定理解时，禁止从“没看懂”直接跳到 `sex / age` 等字段问题

### 7.6.1 `opening_clarify` 原则

`opening_clarify` 用于首轮疑似错字、乱码、打字异常或无法稳定理解的输入。

统一范式：

1. 先轻澄清
2. 再回到开场分流
3. 不直接采字段

可接受的话术特征：

- 先承认“我这句有点没看懂 / 没太接住 / 没看明白 / 没反应过来”
- 再轻量确认用户来意，如“你是想找对象，还是先了解下呀？”
- 允许多变体，不固定一句模板

禁止行为：

- 先说“是不是打错字了”再直接追问 `sex`
- 用澄清当跳板，下一句立刻切 `age / location / education`
- 把 `opening_clarify` 写成客服式纠错公告

### 7.7 时间型打招呼校正原则

时间型打招呼属于 `opening_connective` 的特殊子类，必须结合系统当前真实时间做轻校正。

支持范围至少包括：

- `早上好`
- `早安`
- `上午好`
- `下午好`
- `晚上好`
- `晚安`
- `早啊`
- `晚上好在吗`

处理规则：

1. 先识别为 `opening_connective`
2. 若命中时间型问候词，再与系统当前真实时间段做比对
3. 若时间一致，正常回复
4. 若时间不一致，轻纠正后再回到开场连接分流

校正要求：

- 不能被用户输入的时间词带偏
- 不能机械复读用户的错误时间问候
- 纠正语气要轻，不要显得刻意或挑错
- 纠正后仍要继续探测用户来意

例如：

- 用户早上说 `晚上好`
  - 不应回复 `晚上好呀`
  - 应类似回复：
    - `哈哈，现在还是早上呢。你这边是想找对象，还是先了解下呀？`
- 用户下午说 `早安`
  - 不应回复 `早安`
  - 应类似回复：
    - `现在已经下午啦。你这边是想找对象，还是先看看情况呀？`

组合型时间问候同样适用：

- `晚上好在吗`
- `早安，你在吗`
- `下午好哈喽`

它们都不应掉回字段采集，而是应先完成时间校正，再继续 `opening_probe`

### 7.8 中等字段并问原则

中等字段整体仍以自然穿插为主，但 `monthly_income` 从本版本开始单独后置处理，不再按普通中等字段并问。

推荐搭配：

- `location + partner_requirement`
- `marital_status + partner_requirement`
- `education + occupation`
- `location + occupation`

规则说明：

- 中等字段平时弱化存在感，不抢主线
- 优先跟在语义相邻的核心字段后面自然带出
- 只有当中等字段成为 Coverage 的唯一阻塞项时，才允许单独升级为兜底目标
- 这里的“推荐搭配”是优先级，不是固定绑定关系；实现必须支持动态换宿主

对 `monthly_income` 的补充约束：

- `monthly_income` 不再和核心字段拼接问
- `monthly_income` 不作为 `side_target`
- `monthly_income` 不参与前期主线压缩轮次
- 只有在核心字段全部完成后，才允许单独弱问一次

补充口径：

- 当用户首轮已经给出 `location + occupation` 时，下一步优先补低压核心字段，如 `age` 或 `education`
- `monthly_income` 在这类场景下不主动问，继续后置

### 7.9 最新字段邻近优先原则

从本版本开始，字段调度不只看“全局还缺什么”，还要看“用户刚刚这句重点给了什么”。

统一要求：

- 用户刚主动给出的字段，优先作为下一问的局部路由依据
- 下一问应优先从这个字段的语义邻近字段里选，而不是马上回到全局固定顺序
- 这条规则适用于首轮主动给资料，也适用于后续轮次中的短答补充

推荐邻近关系：

- 用户刚给出 `location`：
  - 优先下一问 `occupation`
  - 其次 `education`
  - 再其次 `age`
- 用户刚给出 `occupation`：
  - 优先下一问 `education`
  - 其次 `age`
-  - 不默认追问 `monthly_income`
- 用户刚给出 `age`：
  - 优先下一问 `location`
  - 其次 `education`
  - 再其次 `occupation`
- 用户刚给出 `education`：
  - 优先下一问 `occupation`
  - 其次 `location`
- 用户刚给出 `location + occupation`：
  - 优先补低压核心字段，如 `age` 或 `education`
  - 不默认直接主问 `monthly_income`

示例口径：

- 用户说：`男的呢，在深圳`
  - 更顺的下一步应优先问工作，而不是立刻回去问年龄
- 用户说：`90后，深圳，做IT`
  - 更顺的下一步应优先补 `education / marital_status` 等缺失字段，而不是回头重问城市或工作

补充说明：

- 这里的“邻近优先”不是随机跳字段，也不是完全固定顺序
- 系统会先看用户这一轮刚刚明确给出的资料，再从语义更顺的相邻字段里选下一问
- 只有当当前轮没有明显资料落点时，才回到受控主线顺序
- 目标是减少“表单回跳感”，让追问更像顺着用户刚说的话往下聊

当前口径下，核心字段推进应遵守以下关系：

- 用户刚给出 `location`
  - 优先下一问 `occupation`
  - 其次 `education`
- 用户刚给出 `occupation`
  - 优先下一问 `education`
- 用户刚给出 `age`
  - 优先下一问 `sex`
  - 其次 `location`
- 用户刚给出 `education`
  - 优先下一问 `marital_status`
- 用户刚给出 `sex`
  - 优先下一问 `location`
  - 其次 `occupation`
- 用户刚给出 `location + occupation`
  - 优先补低压缺失核心字段，如 `education / age / sex`

边界要求：

- 邻近优先只是在“当前缺失字段集合”里做局部路由，不允许越过未完成核心字段直接跳联系方式
- 邻近优先不改变“核心优先于中等字段”的总原则
- `marital_status / partner_requirement` 仍属于中等或准核心穿插字段，不能因为当前轮语义接近就长期抢占主线
- `monthly_income` 单独后置，不参与前期邻近穿插

### 7.9.1 中等字段自然拼接规则

`marital_status`、`partner_requirement` 这类字段，不应理解为独立主线字段，也不应机械理解成固定绑定关系。`monthly_income` 另按后置收入信息字段处理。

统一原则是：

- 先确定当前 `main_target`
- 再判断是否存在当前最相近、最自然、最顺口的 `side_target`
- 中等字段默认不单独抢主问
- 只有在成为 Coverage 唯一阻塞项时，才允许升级为兜底目标

这里强调的是“优先拼接关系”，不是“固定绑定关系”。

执行口径：

- 优先和当前最相近的字段拼接问
- 如果最相近字段已经在前文由用户主动明确给出，也可以和当前最顺的字段自然拼接
- 代码只决定“现在和谁拼接最自然”，具体怎么说完全交给 AI 生成
- 不允许为了追中等字段，生硬打断当前更自然的主线推进

当前推荐拼接优先级：

- `marital_status`
  - 第一优先：`age`
  - 第二优先：`location`
  - 第三优先：`education / occupation`
  - `sex` 不是优先宿主，不建议默认硬拼
  - 如果当前轮不是最优宿主，但仍处在基础资料了解阶段，也可以顺着当前最自然的基础字段带出
  - 问法应优先是开放式婚况/感情状态确认，不应默认窄化成“单身确认”
- `partner_requirement`
  - 第一优先：`age`
  - 第二优先：`location`
  - 第三优先：`occupation`
  - 再其次才考虑 `education / marital_status`
  - 不建议和 `sex` 硬拼
  - 从“你自己的情况”过渡到“你想找什么样的人”更自然时再带出
  - 如果已经知道 `partner_gender_preference`，这里追问的是“除此之外更看重什么”，而不是再追问性别方向

补充约束：

- 中等字段永远找语义最近的未收核心字段挂靠，不固定死模板
- 如果当前没有合适宿主，就单独问，不强拼
- 问题预算控制只允许删整问，不允许裁成残句
- 例如：
  - 可以回退成只问 `学历`
  - 不能出现 `你是什么学历呀，大概的` 这种半截话

### 7.9.2 `monthly_income` 后置规则

从本版本开始，`monthly_income` 统一按“收入信息字段”后置处理，不再作为普通中等字段参与自然拼接。

执行口径：

- `monthly_income` 只允许在以下 5 个核心字段全部进入完成态后，再单独弱问一次：
  - `sex`
  - `age`
  - `education`
  - `occupation`
  - `location`
- 这里的“完成态”仅包括：
  - 已收集
  - 已有效询问 2 次未答，进入跳过态
- 如果上述核心字段中任一字段仍未完成，则不主动询问 `monthly_income`
- 如果上述核心字段中任一字段为明确拒绝态，则不主动询问 `monthly_income`
- 如果用户前面疑虑明显、FAQ 频繁、联系方式仍在协商，或整体配合度不高，则不主动询问 `monthly_income`
- `monthly_income` 仅允许单独弱问一次；用户不答即跳过，不再主动强追
- 对外询问统一按“收入信息”表达，不限定只问月薪；允许用户回答月薪、年薪或收入区间
- 允许弱化表达，但不形成固定模板；策略层只约束语气和时机，不固定句子

### 7.9.3 多数字长句与高风险短路约束

从本版本开始，涉及年龄、收入、身高、联系方式、择偶年龄差等多数字混合长句时，统一遵守以下约束：

- 先做数字语义角色归类，再决定字段落槽
- 高风险短路必须优先消费统一理解链结果，不允许业务旁路自己重新 parse 原句数字
- 当同句存在多个数字语义角色，且当前判断会直接触发结束态/限制态时，必须先走 AI 上下文复核
- 当前阶段不允许通过 fallback 裸猜数字参与高风险结束判断

执行口径：

- `age_under_limit` 只允许基于稳定的本人年龄结论触发
- `partner_age_gap`、`partner_age_range` 不能反向污染 `age`
- `income / height / weight / contact` 等数字字段同样必须按角色消费，不允许“谁先命中谁赢”
- 如果统一理解结果不稳定，宁可继续主流程，也不允许误杀正常用户

补充执行口径：

- 当 AI 已经把多数字长句拆成 `self age`、`partner_pref_age`、`partner_requirement` 等结构化字段后，后链路不得重新用数字规则竞争字段归属
- 数字类后处理只允许校验值是否合法，不允许重判“这个数字到底属于谁”

- 先确定 `main_target`
- 再对 `marital_status / partner_requirement` 做候选评分
- 评分至少考虑：
  - 当前 `main_target` 是否在该字段的优先宿主列表里
  - 用户这句刚给出的 cue 是否与该字段相邻
  - 该字段是否仍未收集、未超次数、未进冷却
  - 更高优先级宿主字段是否已经在前文收集，可作为历史语境锚点
- 分数最高者成为本轮 `side_target`
- 如果没有候选分数达标，则本轮不带 `side_target`

硬约束：

- 每轮最多 `1 个 main_target + 1 个 side_target`
- 用户有 FAQ / 顾虑 / 投诉时，本轮不带 `side_target`
- 联系方式轮次不带 `side_target`
- 不能因为 `side_target` 更顺，就越过未完成核心字段直接跳联系方式

表达约束：

- 在仍有资料字段待补时，禁止提前使用“你的基本情况我大概有数了 / 我这边差不多了解了 / 我心里有数了”这类阶段总结话术
- 追问 `marital_status / partner_requirement` 时，优先承接本轮刚收到的局部信息，不要制造“画像已经差不多收齐”的体感

纠偏说明：

- 问两个信息点本身不是问题
- `婚况`、`择偶要求` 本来就允许且应该和相近字段融合追问
- `monthly_income` 不再纳入这类融合追问，统一后置单独弱问
- 真正要避免的是把融合追问做成固定模板拼句，导致流程感、表单感过强
- 文档约束的是“拼接优先级、语义边界和推进规则”，不是要求某一种固定句式

### 7.10 明确求偶意图时的开放自述入口

当用户已经明确表达“想找对象”，但还没有提供任何资料时，系统不必每次都立刻进入硬字段提问。

允许策略：

- 先承接用户的求偶意图
- 在一部分轮次里，给用户一个开放自述入口
- 用户如果愿意主动介绍自己，就顺着他的自述抽取字段并继续推进

推荐口径：

- `好呀，那我先简单了解下你。你也可以先简单说说自己，我顺着了解会更自然一点。`
- `行呀，你要不先简单介绍下自己，我顺着了解会更顺一点；或者我先问你一个小问题也行。`

边界要求：

- 这不是每轮默认动作，只在用户明确表达求偶意图、且当前没有 FAQ / 边界 / 顾虑阻塞时使用
- 开放自述入口后，下一步仍要回到主线资料收集
- 不能因为开放自述而放弃核心字段收集

产品收益：

- 给用户更多主动权，降低“被盘问”感
- 更容易拿到系统平时不主动问的被动字段，如称呼、身高、体重
- 更容易让用户一次性说出多个核心字段，从而让后续问题更自然地顺着聊

### 7.11 用户疑虑优先于资料收集

当用户对“为什么要问 / 为什么要记 / 收集这些干嘛 / 为什么一直问这些资料”表达顾虑时，本轮必须先答疑，不能继续推进字段采集。

识别实现：

- 使用独立 `collection_concern_detector`
- detector 输入：
  - `message`
  - `last_asked_field`
  - `last_response`
  - `recent_responses`
  - `in_contact_flow`
- detector 输出：
  - 是否命中 `info_collection_why`
  - 命中置信度
  - 命中原因 `reasons`
  - 命中的上下文字段 `context_field`

判定信号：

- 词库兜底：
  - `为什么要记下我的信息`
  - `收集这些信息干嘛`
  - `为什么一直问这些资料`
  - `为什么要问这么细 / 为啥要问这么清楚 / 为啥要问这么清晰`
- 疑问信号：
  - `为什么 / 为啥 / 干嘛 / 做什么 / 有必要吗`
- 强度信号：
  - `这么细 / 这么清楚 / 这么清晰 / 这么多 / 一直问 / 老问`
- 收集行为信号：
  - `记 / 记录 / 收集 / 留 / 问 / 了解 / 确认`
- 对象信号：
  - `信息 / 资料 / 情况 / 这些 / 这个 / 内容`
- 上下文信号：
  - 上一轮正在问 `学历 / 婚况 / 月薪 / 择偶要求 / 电话 / 微信`

裁决原则：

- 直接词库命中时直接判成 `info_collection_why`
- 无上下文时，至少要满足“疑问信号 + 收集行为/对象语义”才命中
- 有上下文时，允许“疑问信号 + 强度信号 + 上下文字段”直接命中
- 这类识别不能只靠枚举句子，必须让上下文有更高优先级

命中后的执行要求：

- 本轮 `prioritize_user_question=True`
- 本轮不追问资料
- 本轮不推进电话/微信
- 本轮不记录字段有效询问次数
- 先答清楚，下一轮再恢复主线

恢复主线要求：

- FAQ / 顾虑轮即使本轮 `ask_field=None`，也要保存被打断的真实追问字段到 `resume_profile_target`
- 恢复目标优先级：
  - `last_asked_field`
  - 上一轮回复里实际问到的字段
  - 兜底使用当前策略重新算出的主目标
- 用户下一轮如果只回复 `好 / 好的 / 嗯 / 知道了` 这类确认语，且上一轮属于 FAQ 解释轮，要直接恢复 `resume_profile_target`
- FAQ 解释轮不允许把策略层临时算出的下一个候选字段覆盖掉已保存的被打断字段

## 8. 四个 Gate

## 8.1 Coverage Gate

Coverage Gate 只回答一个问题：

- 该问的字段轮次，走完没有

核心字段覆盖完成条件：

```python
core_covered = collected or ask_count >= 2
```

中等字段覆盖完成条件：

```python
medium_covered = collected or ask_count >= 1
```

Coverage Gate 通过条件：

```python
coverage_passed = all_core_covered and all_medium_covered
```

这里的关键不是公式本身，而是 `ask_count` 的语义：

- `ask_count` 不再等于“AI 提过几次”
- `ask_count` 表示“有效覆盖尝试次数”

只有在一次字段推进真正成立时，才计入 `ask_count`。

只要 `coverage_passed=False`，就不能进入联系方式。

## 8.2 Profile Sufficiency Gate

Profile Sufficiency Gate 只回答一个问题：

- 虽然该问的都问过了，但画像会不会太空，不适合切联系方式

规则：

```python
profile_sufficient = core_success_count >= 3
```

只统计：

- `sex`
- `age`
- `education`
- `occupation`
- `location`

注意：

- `profile_sufficient` 不是提前放行条件
- 它只能在 `coverage_passed=True` 后再生效

## 8.3 Turn Quality Gate

Turn Quality Gate 只回答一个问题：

- 当前这一轮，适不适合切联系方式

以下场景通常不适合切联系方式：

- 用户在提问题
- 用户在表达顾虑
- 用户在投诉
- 当前轮本来就该轻承接
- repair mode 修复中
- 当前轮是边界收口轮

输出：

```python
turn_quality_passed: bool
```

## 8.4 Cost Control Gate

Cost Control Gate 只回答一个问题：

- 还值不值得继续高成本推进

输出投入模式：

- `full`
- `compact`
- `light`
- `close`

含义：

- `full`：正常推进
- `compact`：压缩推进
- `light`：轻答，不主动推进
- `close`：停止主流程，礼貌收口

当前版本建议使用这些计数器：

- `non_cooperation_turns`
- `off_topic_turns`
- `open_profile_attempts`
- `session_token_spent`（如已有）

建议阈值：

- 连续不配合 >= 3：转 `light`
- 连续跑题 >= 3：转 `light`
- 开放式补画像失败 >= 2：转 `light`
- token >= 20000：转 `compact`
- token >= 35000：转 `light` 或 `close`

## 9. 字段级结果判定

为了让 `ask_count` 语义稳定，当前目标字段每轮只判 4 类。

### 9.1 `answered_target`

含义：

- 用户答到了当前主目标字段

例子：

- AI：你现在在哪个城市？
- 用户：我在深圳

处理：

- 当前字段收集成功
- 当前字段不再追问

### 9.2 `answered_other_field_only`

含义：

- 用户没答当前主目标字段
- 但答了别的有效字段

例子：

- AI：你现在在哪个城市？
- 用户：我做 IT

处理：

- 更新答到的字段
- 当前目标字段不算完成
- 当前目标字段第一次不记失败
- 下一轮给一次补问机会

### 9.3 `evaded_target`

含义：

- 用户明确回避当前主目标字段
- 或连续两次都错位跳过当前主目标字段

例子：

- 用户：这个先不说
- 或连续两轮只答别的字段，不答当前目标

处理：

- 当前目标字段 `ask_count` 增加 1

### 9.4 `interrupted_by_concern`

含义：

- 用户没有接字段，而是提问题、表达顾虑、质疑、投诉

例子：

- “线下有门店吗”
- “你们是不是骗子”
- “为什么要问这个信息”

处理：

- 当前字段 `ask_count` 不增加
- 本轮先答疑
- 下一轮恢复原目标

## 10. Coverage 只消费哪两类结果

Coverage 只消费：

- `answered_target`
- `evaded_target`

Coverage 不消费：

- `answered_other_field_only`
- `interrupted_by_concern`

原因：

- `answered_other_field_only` 说明用户只是答错位，不代表当前目标字段已经被问过并完成覆盖
- `interrupted_by_concern` 说明这一轮被用户疑问打断，不代表字段推进失败

## 11. 用户疑问优先机制

当 AI 正在推进核心字段或中等字段时，如果用户提问、质疑、表达顾虑或投诉，则：

- 本轮先答疑
- 本轮不推进字段
- 本轮不推进联系方式
- 当前字段不消耗 `ask_count`
- 保存：
  - `resume_profile_mode`
  - `resume_profile_target`
  - `last_user_concern_type`

下一轮如果用户不再继续追问，就优先恢复原目标。

恢复规则采用最简实现：

- 保存一次
- 恢复一次
- 恢复后立即清空

不引入多轮有效期。

## 12. 错位回答规则

如果用户没有回答当前目标字段，而是回答了别的字段：

第一次错位：

- 视为 `answered_other_field_only`
- 更新用户答到的字段
- 当前目标字段 `ask_count` 不增加
- 下一轮补问当前目标字段一次

连续第二次错位：

- 视为 `evaded_target`
- 当前目标字段 `ask_count` 增加 1

因此：

- 第一次答错字段，不立刻算拒绝
- 连续错位，才算一次有效未覆盖尝试

## 13. 双问题自然提问保留，但后台必须有主次

婚况、择偶要求继续保留当前产品设计：

- 穿插问
- 自然结合其他字段问
- 不改单问硬问

`monthly_income` 例外：

- 不再和其他字段双问题并问
- 不再作为穿插 side ask
- 统一后置到核心字段完成后，再单独弱问一次

这里的“自然结合”进一步明确为：

- 优先和当前最相近、最自然的字段拼接
- 如果强相关字段已在前文被用户主动交代，也可以和当前最顺的字段拼接
- 不是固定绑定，不是固定话术，也不是固定转折词
- 最终句子必须由 AI 自己生成，策略层只提供主次关系和语义约束

但后台必须维护：

- 一个 `main_target`
- 一个可选 `side_target`

实现补充：

- `last_question_state` 不能只记录第一问或主句命中的字段。
- 只要同一轮回复里真实问到了 `main_target + side_target`，状态层就必须同时保留两者。
- 问句检测词典必须和实际生成模板对齐，尤其是：
  - 年龄类问法：`哪一年的 / 几几年的 / 哪年出生`
  - 婚况类问法：`感情状态 / 婚况 / 单身状态`
  - 收入类问法：`收入大概在哪个区间 / 收入区间`
  - 择偶偏好类问法：`更看重哪一点 / 更在意哪方面`
- 否则用户下一轮如果按“双答”同时回答，未被记录成 `side_target` 的字段会在权限层被误过滤，表现为“用户明明答了，但系统没收进去”。

如果用户只回答了 `side_target`：

- 更新 `side_target`
- `main_target` 仍未完成
- 下一轮补 `main_target`

如果用户只回答了 `main_target`，没有回答 `side_target`：

- 更新 `main_target`
- `side_target` 进入 `pending_followup`
- 下一轮优先补这个未回答的 `side_target`
- 不允许直接无故滑向新的不相干字段

## 14. `partner_requirement` 规则

字段口径先明确：

- `partner_requirement` 表示对另一半的特质 / 条件偏好
  例如：`温柔`、`成熟稳重`、`年龄合适`、`同城`
- 性别偏好不再混装进 `partner_requirement`
  例如：`想找男朋友`、`喜欢男生`、`偏女生`
  应单独落到 `partner_gender_preference`

因此后续追问口径也要统一：

- 如果已经知道 `partner_gender_preference`，再问 `partner_requirement` 时，问题应明确变成：
  - `除了偏男生/偏女生这点之外，你还会更看重哪一点？`
- 不能再把 `男生/女生` 当成 `partner_requirement` 已完成
- 用户如果只回答了性别偏好，系统应记下性别偏好，并继续追真正的特质 / 条件偏好

保留现有原则：

- 平时是 `side_target`
- 不是主线硬问

增加兜底规则：

如果：

- 核心字段都已覆盖
- 联系方式还不能进入
- 未覆盖项只剩中等字段
- 特别只剩 `partner_requirement`

则允许：

- `partner_requirement` 升级成 `forced_cover_target`

如果它被用户疑问打断：

- 不消耗那一次覆盖机会
- 下一轮恢复继续问

## 15. Coverage 通过但画像不足时

当：

- `coverage_passed=True`
- `profile_sufficient=False`

则：

- 不进入联系方式
- 不回退到机械逐字段流程
- 进入 `open_profile_repair`
- 最多尝试 1 到 2 次

如果仍然不足：

- 进入 `low_pressure_chat`

当前版本不记录开放式补画像的目标字段，只保留轻量实现。

## 16. 联系方式进入条件

只有同时满足：

```python
can_enter_contact = (
    coverage_passed
    and profile_sufficient
    and turn_quality_passed
    and engagement_mode in {"full", "compact"}
)
```

才允许进入联系方式。

## 17. 联系方式流冻结规则

一旦联系方式流开始，主资料流冻结。

判定联系方式流已开始的条件：

- `phone_ask_count > 0`
- 或 `wechat_ask_count > 0`
- 或 `phone_collected = True`
- 或 `wechat_collected = True`
- 或 `rejected_phone = True`
- 或 `rejected_wechat = True`

只要满足任一，就认为已经进入或处于联系方式流。

此时：

- 不再主动推进核心字段
- 不再主动推进中等字段
- 不再重新选择资料类 `main_target`
- 不再触发 `forced_cover_target`
- `side_target = None`
- 只继续当前联系方式流程
- 如果用户主动补资料，只做被动提取，不主动追问

## 18. “无有效推进”的统一定义

新增一个轻量布尔规则：

- `made_effective_progress`

它只回答一个问题：

- 这轮有没有让主流程往前走半步以上

判定为 `True` 的情况，满足任一即可：

1. 收到了当前 `main_target`
2. 收到了其他核心/中等有效字段
3. 联系方式流有实质推进
4. 用户顾虑被成功处理，并允许恢复主流程

判定为 `False` 的情况：

1. 纯 FAQ 循环
2. 纯质疑/顾虑循环，且没有缓和
3. 纯寒暄、确认词、敷衍词
4. 连续错位回答，没有命中当前目标，也没有新增关键字段
5. 本轮既没字段推进，也没联系方式推进，也没解除用户顾虑

这条规则只用于：

- 更新 `non_cooperation_turns`
- 更新 `off_topic_turns`
- 辅助 `Cost Control Gate`

不单独做成新 Gate。

## 19. 决策顺序

每轮严格按下面顺序：

1. 先算 `Coverage Gate`
2. 再算 `Profile Sufficiency Gate`
3. 再算 `Turn Quality Gate`
4. 再算 `Cost Control Gate`
5. 如果用户疑问优先，则本轮先答疑并保存 `resume_target`
6. 如果联系方式流已开始，则冻结主资料流，只走联系方式
7. 基于结果决定 `next_mode`
8. 再决定本轮 `main_target / side_target / forced_cover_target / allow_contact_push`

## 20. `next_mode` 规则

```python
if has_ongoing_contact_flow(profile):
    next_mode = "contact_flow"
elif not coverage_passed:
    if unresolved_core_fields:
        next_mode = "collect_core"
    else:
        next_mode = "collect_medium"
elif not profile_sufficient:
    if open_profile_attempts < 2 and engagement_mode in {"full", "compact"}:
        next_mode = "open_profile_repair"
    else:
        next_mode = "low_pressure_chat"
elif not turn_quality_passed:
    next_mode = "contact_hold"
elif engagement_mode in {"light", "close"}:
    next_mode = "low_pressure_chat" if engagement_mode == "light" else "terminate_conversion"
else:
    next_mode = "contact_flow"
```

## 21. 下一步目标生成规则

如果当前不能进联系方式，并且又不在联系方式流中，就必须保证有下一步目标：

1. 先找未覆盖核心字段
2. 如果核心都覆盖了，再找未覆盖中等字段
3. 如果只剩 `partner_requirement`，允许它成为 `forced_cover_target`
4. 如果 `coverage_passed=True` 但画像不足，进入 `open_profile_repair`
5. 只有真正无事可做时，才允许轻收尾

也就是说：

- `ask_field=None` 不能裸跑给模型
- 一旦进入联系方式流，则不再回头主动找资料字段目标

## 22. 对话承接规则

每次推进字段前，优先做承接，不要直接硬问。

承接顺序：

1. 承接用户情绪
2. 承接用户内容
3. 给一句轻反馈
4. 再推进主目标字段

示例逻辑：

- 用户积极回答：轻反馈后继续推进
- 用户犹豫：先安抚，再降低问题压力
- 用户开玩笑：可轻接一句，再回主线
- 用户敷衍：不要立刻压问，先换轻方式
- 用户防备：先解释用途，再决定是否继续问

## 23. 转场规则

从一个字段切到另一个字段时，必须经过转场。

标准转场结构：

`承接上一句 → 反馈/认可 → 进入下一字段`

禁止：

- 刚问完职业，下一句直接问收入
- 刚问完年龄，下一句直接问婚况且无过渡

补充约束：

- 即使职业刚收齐，也不直接顺手追问收入
- 收入信息只能在核心字段全部完成后，单独开启一轮弱问

### 23.1 禁止开场白的执行口径

“禁止开场白”只表示：

- 禁止重复系统欢迎语
- 禁止重复自我介绍型固定开场

不表示：

- 禁止短承接
- 禁止一句轻反馈后再推进字段

执行口径：

- 非首轮：禁止重复欢迎语，但允许 1 句承接 + 1 个轻问题
- 首轮纯问候：必须先承接，再推进

## 24. 首轮体验原则

首轮用户体验优先级：

`接住用户 > 建立信任 > 给用户选择感 > 再推进字段`

首轮明确要求：

- 用户第一句是纯问候时，必须先自然承接，不得直接抛字段问题
- 不允许因为已有某个字段默认值就跳过问候承接
- 首轮可推进字段，但必须是“承接后轻推进”

## 25. 非收集型互动规则

为了更像真人，允许少量非收集型互动。

规则：

- 每收集 2 到 3 个有效字段，可插入 1 轮轻互动
- 轻互动只做短反馈，不长聊
- 下一轮必须回到主线

可做：

- 简短认可
- 轻微共情
- 对择偶表达做一句自然反馈

不可做：

- 连续两轮不收集
- 输出大段建议
- 变成陪聊

## 26. 用户控制权规则

首轮或关键转场轮，允许给用户一个轻量选择：

- “我先快速了解你两三点”
- “你先说你最在意的”

规则：

- 仅提供 2 个短选项，不做复杂分支问卷
- 选项必须口语化、低压力
- 用户未选择时，默认走“先听用户说，再轻推进”

## 27. 用户类型适配

| 用户类型 | 特征 | 对应策略 |
|---|---|---|
| 配合型 | 回答直接，信息量高 | 推进稍快，允许 1主 + 1顺带 |
| 保守型 | 回答短，对敏感问题回避 | 多解释、少压迫、少追问 |
| 敷衍型 | “嗯”“还行”“再说吧”较多 | 放慢推进，更多被动提取 |
| 话题型 | 愿意展开讲要求、生活、经历 | 先顺着聊，再从中提取字段 |

## 28. 记忆回用规则

用户已经说过的信息，后续回复里要自然回用。

规则：

- 回用要短，不要像复读资料
- 回用的目的是让用户感到“被听见了”

允许的回用：

- 地区
- 职业
- 择偶要求
- 已表达的偏好
- 已表达的顾虑

禁止：

- 大段重复用户资料

### 28.1 上下文承接硬约束

“记忆回用”不能只停留在提示词层，必须进入主流程决策。

系统每轮不只判断“下一步问什么”，还必须判断“这一轮先接什么”。

统一要求：

1. 先识别当前轮主落点
2. 再决定下一步动作
3. 回复必须先承接当前轮主落点，再推进主线或支线动作

当前轮主落点至少包括：

- `work_busy`
  - 例如：`我工作比较忙`
- `location_reuse`
  - 例如：`那边有什么好的相亲资源吗`
- `preference_reuse`
  - 例如：`有什么推荐吗`
- `faq_followup`
  - 例如：`你们怎么匹配`、`为什么要留电话`
- `boundary_pause`
  - 例如：`这个我不太方便说`
- `topic_shift`
  - 例如：`先不聊资料`
- `profile_partial_with_boundary`
  - 例如：`本科，不过这个先不太方便说`

执行口径：

- 当前轮命中主落点后，本轮回复必须先接住该落点
- 不能跳过承接，直接切到字段采集或联系方式推进
- FAQ 轮先答 FAQ，不得借答疑顺手要电话/微信
- `boundary_pause` / `topic_shift` / `profile_partial_with_boundary` 轮优先降压，不直接追字段
- `work_busy` / `location_reuse` / `preference_reuse` 轮，回复开头必须体现用户刚刚说的工作、城市、偏好等语义

这条规则是“动作约束”，不是“固定句式约束”：

- 固定的是：先承接，再推进
- 不固定的是：具体用哪一句话

禁止实现方式：

- 把 `work_busy` 固定成唯一一句模板
- 把 `location_reuse` 固定成唯一一句模板
- 把“承接上下文”实现成机械资料复读
- 只靠提示词提醒“先承接”，不做决策约束和交付校验

允许实现方式：

- 决策层输出 `followup_topic / context_ack_required / context_ack_type`
- 表达层按语义槽位生成多变体承接
- 交付前校验“是否真的接住了当前轮主落点”

### 28.2 非固定话术原则

上下文承接必须避免退化成固定模板系统。

统一要求：

- 固定策略结构，不固定具体句面
- 可以有多变体表达，但不能长期复读同一句
- 同一个 `context_ack_type` 允许不同句式、不同口语词、不同长度
- 重点是语义命中，而不是模板命中

例如 `work_busy`：

- 可接受：
  - `工作忙我能理解。`
  - `平时工作节奏比较满是吧。`
  - `做这类工作忙起来确实挺正常。`
- 不可接受：
  - 永远固定输出同一句

例如 `preference_reuse`：

- 可接受：
  - `你会更看重成熟稳重这一类，对吧。`
  - `成熟稳重这个点你是比较在意的。`
  - `你更偏向相处稳一点的类型。`
- 不可接受：
  - 每次都机械复读用户原话

### 28.3 交付前校验

“接住上下文”不能只靠生成模型自觉，必须在最终交付前做校验。

统一要求：

- 如果当前轮标记为 `context_ack_required=True`
- 但最终回复没有体现对应主落点语义
- 却直接进入字段追问、联系方式推进或空泛收口
- 则判定为 `context_drop`

`context_drop` 是需要被拦截并重写的交付错误，不是可接受的话术波动。

## 29. FAQ 与业务边界统一口径

以下 FAQ 场景统一按“先解释，再保持边界”处理：

- 收费
- 门店
- 怎么匹配
- 为什么要留电话/微信
- 能不能直接加对方
- 能不能先看照片
- 多久能安排 / 多久能找到
- 平台靠不靠谱 / 安不安全

统一要求：

- 可以解释，但不要讲成承诺
- 可以自然，但不要讲成营销
- FAQ 轮不要顺手切回资料收集

### 29.1 推荐表达方向

联系方式用途：

- 推荐说法：后面沟通更方便、后续确认会更顺一点
- 禁止说法：有合适的人选时第一时间联系你、给你发资料

门店/线下：

- 推荐说法：有线下门店，具体怎么安排以后续沟通为准
- 禁止说法：匹配后给你发具体定位、安排线下见面

照片/资料：

- 推荐说法：这类内容不是当前阶段直接发的，会先看沟通和隐私边界
- 禁止说法：双方合适后互换照片、先把资料发你

流程/匹配：

- 推荐说法：先了解基本情况和偏好，后面再继续沟通
- 禁止说法：马上安排、马上出结果、明确时效承诺

## 30. 低信息回复规则

用户若只回以下低信息表达：

- 好
- 好的
- 嗯
- 行
- 可以
- 回头再说

执行口径：

- 不要误判为用户已提供联系方式
- 不要机械复读上一轮问题
- 电话推进过一次后，低信息确认可自然切到微信方案
- 双渠道都推进过后，低信息确认应暂停联系方式推进
- “回头再说”优先按边界/暂缓处理，不再继续硬推联系方式

## 34. 技术落地建议

建议拆成 5 层（先理解，再提取，再决策，再回复）：

| 模块 | 职责 |
|---|---|
| AI 结构化理解层 | 对用户原话做多意图理解：本人信息、择偶要求、FAQ/顾虑、联系意图，并给出 `direct_write` 候选 |
| 字段提取与提交层 | 将 AI 结果标准化并提交：`accepted(committed)` 一经成立，不允许后链路改义 |
| 字段调度层 | 决定当前 `main_target`、`side_target`、`forced_cover_target`，并处理恢复目标 |
| 表达层 | 负责承接、转场、问法层级、FAQ 回答边界 |
| 联系方式层 | 继续使用现有独立逻辑 |

最小实现顺序：

1. 先打通 AI 结构化理解层（同步阻塞本轮决策）
2. 再打通字段提取与提交层（落实 AI-first 提交契约）
3. 再做字段优先级与 Gate 决策
4. 再做用户疑问优先与恢复 + 中等字段穿插与 `partner_requirement` 兜底
5. 再做联系方式冻结与“无有效推进”成本控制

## 36. 当前实现口径

当前项目中，这套方案已经接入主流程，后续实现和修正都应继续遵守本文档口径：

- 4 Gate 是唯一主判断框架
- 字段推进统一按“有效覆盖尝试次数”而不是“AI 提过几次”
- 答疑轮不消耗当前字段覆盖次数
- 第一次错位回答不立刻记为拒绝
- 联系方式流一旦开始，主资料流冻结
- `made_effective_progress` 统一驱动运行态计数与降级逻辑

## 37. 最终产品规则，压缩版

1. 核心字段完成标准是“收集成功或有效覆盖尝试满 2 次”。
2. 中等字段完成标准是“收集成功或有效覆盖尝试满 1 次”。
3. 联系方式不参与核心/中等字段覆盖完成判断。
4. 所有核心和中等字段都完成覆盖后，才有资格进入联系方式判断。
5. 即使覆盖完成，核心成功数不足 3，也不进入联系方式，而先做开放式补画像。
6. `partner_requirement` 平时穿插问，但成为唯一阻塞项时可临时升级为兜底目标。
7. 用户提问、质疑或顾虑时，本轮先答疑，不消耗当前字段覆盖次数，下一轮恢复原目标。
8. 用户第一次答错字段不算拒绝，连续错位才算一次有效未覆盖尝试。
9. 一旦联系方式流开始，主资料流冻结，只继续处理联系方式；资料只做被动提取，不再主动追问。
10. 若本轮既未推进字段、未推进联系方式、也未消除用户顾虑，则判定为“无有效推进”，用于驱动轻答或收口。

## 38. 长句高质量理解与稳定收集最终方案（新增必做）

### 38.1 当前问题的根因复盘

针对“用户发一大段话，系统收集不到完整信息”的问题，根因不是单点，而是链路耦合导致：

- 同步语义抽取超时阈值过紧（典型 4 秒）且无有效重试，导致结构化理解经常失败后走 fallback。
- 长句混合意图（本人信息 + 择偶要求 + FAQ + 联系方式）时，后置权限过滤或高风险策略会抑制部分字段。
- AI 已正确识别的字段在后链路被二次语义改判，出现“前面识别对了，后面被挡掉/改掉”。
- 状态确认（如出生年确认）与主线采集未解耦，导致持续追问同一字段，压制其它已识别信息入档。
- `ask_field` 与最终回复问句缺乏一致性校验，出现“决策问 A，文案问 B”的错位。

### 38.2 为什么仍然必须有同步语义抽取

同步语义抽取不是为了“更复杂”，而是为了保证本轮正确决策：

- 本轮是否能正确“先理解→再提取→再决策→再回复”，取决于本轮结构化理解结果。
- 异步 backfill 只能补档，不能影响当前轮已经发出的回复，无法防止“用户明明说了又被追问”。
- 因此必须保留“同步 AI 结构化理解为主，异步补偿为辅”的架构。

### 38.3 统一主链（强制执行）

每轮固定按以下顺序执行，不允许跳步：

1. 理解：AI 结构化理解用户原话（含多意图拆分）。
2. 提取：字段标准化与归属判定（本人/择偶/联系方式/FAQ）。
3. 决策：基于已提交字段决定 `main_target`、`side_target`、`resume_target`。
4. 回复：先承接用户本轮重点，再问最优先剩余问题。

### 38.4 超时治理与时延预算

为解决“AI 结构化理解总超时”，采用预算化调用：

- 主模型同步结构化理解：`timeout = 10~12s`。
- 发生超时/连接错误：立即切备用模型重试 1 次，`timeout = 8~10s`。
- 两次都失败：本轮进入“澄清式回复 + 不破坏已有档案”的降级，不做激进字段覆盖。
- 正常轮目标时延：`4~12s`；长句复杂轮：`12~35s`；极端轮允许到 `<=120s`。

说明：`120s` 是极端上限，不是每轮耗时目标。

### 38.5 提取与落库硬约束（防止“识别对了却没入档”）

- AI 结构化结果中，凡 `direct_write + accepted(committed)` 的字段，必须进入持久化候选。
- 后链路只允许做合法性检查，不允许改写字段语义归属。
- 允许拦截的原因仅限：
  - 格式非法
  - 与稳定旧值冲突
  - CAS 并发失败
  - `soft_confirm`
- 非联系方式字段严禁被 regex/词库/guard 覆写。
- 联系方式字段（phone/wechat）可严格规则校验，但不得反向污染非联系方式字段。

### 38.6 长句混合意图解析要求

面对一条消息中多个意图，必须并行提取，不可只保留一个字段：

- `self_profile`：性别、年龄、地区、学历、职业、婚姻、收入等本人信息。
- `partner_preference`：择偶年龄、身高、收入、地域、职业稳定性等偏好。
- `contact_intent`：手机号、微信号、可联系意愿。
- `faq_or_concern`：收费、真实性、流程、隐私顾虑等问题。

示例约束（必须通过）：

- 输入：`在编教师，喜欢成熟稳重，多金，身高180+`
  - 至少提取：`occupation=在编教师`
  - 同时提取：`partner_requirement`（成熟稳重、多金、身高180+）
- 输入：`找对象 女生找男朋友，目前在深圳未婚单身，本科学历，我自己收入不高一年18左右，找起码180+，90后工作稳定就行`
  - 必须同时提取本人字段与择偶字段，不能只保留一侧
- 输入含 FAQ + 联系方式 + 资料混合时
  - FAQ 可优先回复，但资料字段必须先入档，再决定下一问

### 38.7 决策层硬约束（防重复问、错问）

- 已提交字段不得在后续轮被当作“未收集”重复主动追问。
- 状态确认任务（如出生年确认）不得屏蔽本轮已识别的其它字段入档。
- 如果同轮出现冲突值（如先“90后”后“98年”），保留新鲜值并发起一次明确确认，确认后清理冲突状态。
- 回复生成前必须做 `ask_field` 一致性校验：决策问什么，文案就问什么。

### 38.8 记忆机制（防“聊着聊着忘了”）

记忆必须分层，不可只靠提示词：

- 档案记忆（持久）：已确认用户资料字段。
- 会话记忆（短期）：最近多轮高权重事实与用户刚表达的重点。
- 摘要记忆（中期）：长会话压缩摘要，避免上下文窗口丢失关键事实。

生成回复时必须优先使用“已确认档案 + 当前轮新增字段”，避免重复追问已给信息。

### 38.9 验收指标（上线门槛）

至少监控并达标以下指标：

- `committed_drop_rate = 0`（已 committed 字段不允许被后链路吞掉）。
- `re_ask_after_commit_rate` 显著下降（已给信息重复追问率持续下降）。
- 长句多字段输入的字段召回率显著提升（核心 + 择偶字段同时入档）。
- `ask_field_reply_mismatch_rate` 接近 0（决策字段与最终问句一致）。
- 结构化理解超时率持续下降，并可观测到备用模型兜底命中率。

### 38.10 推荐实施顺序

1. 先改同步结构化理解超时与重试预算（保障可用性）。
2. 再改提取提交契约（保障“识别对了就能落库”）。
3. 再改决策与高风险门控（避免字段被错误抑制）。
4. 最后加交付一致性校验与记忆回用校验（保障拟人稳定性）。

以上四步全部完成后，再做回归压测与灰度放量。
