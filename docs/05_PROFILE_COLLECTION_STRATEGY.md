# 资料收集与 AI 对话统一策略最终方案

## 1. 文档定位

本文档是当前项目中资料收集主流程、AI 对话承接、联系方式切入、成本控制与边界处理的唯一主文档。

后续涉及以下内容时，统一以本文档为准：

- 资料收集字段分层
- 主流程状态机与 `next_mode`
- 进入联系方式的条件
- 用户提问/顾虑时的优先级处理
- 错位回答、回避回答、补问规则
- 联系方式流开始后的冻结规则
- “无有效推进”的统一定义
- 对话承接、转场、FAQ 边界与拟人化口径

## 2. 方案目标

在不改现有统一 prompt 结构的前提下，只优化策略层，解决以下问题：

1. 不再把“收集成功”误当成“流程完成”。
2. 不再因为 `partner_requirement` 之类字段卡死在联系方式前。
3. 不会在画像太空时硬切联系方式。
4. 不会在没有下一步目标时空收尾。
5. 不会被不配合用户持续消耗 token。
6. 用户在字段收集中途提问、表达顾虑或质疑时，系统先答疑，再恢复主流程。
7. 联系方式流开始后，主资料流冻结。
8. 对“无有效推进”给出统一定义，稳定成本控制。
9. 保持对话像真人接话，而不是像填表或跑脚本。

## 3. 范围与非目标

本方案只改策略层，不改：

- 统一 prompt 结构
- AI 的人格与总体表达风格
- 中等字段穿插式收集的产品要求
- 联系方式内部的电话/微信细分流程

本方案当前明确不做：

- 字段敏感度分层
- 恢复目标的多轮有效期机制
- 开放式补画像的目标字段记录
- 额外扩张新的复杂状态机

这些都可以作为后续迭代，但不属于当前版本的必须项。

## 4. 统一术语

### 4.1 收集成功

指某个字段已经拿到可落档值。

### 4.2 覆盖完成

指某个字段虽然不一定收集成功，但已经达到本项目允许的主动推进上限，因此主流程不再依赖它继续机械追问。

### 4.3 有效覆盖尝试

指一次真正成立的字段推进尝试。只有这类尝试才计入 `ask_count`。

### 4.4 无有效推进

指本轮既没有推进字段、也没有推进联系方式、也没有解除用户顾虑。

### 4.5 主目标字段 `main_target`

指本轮最优先推进的字段。每轮只能有一个。

### 4.6 顺带字段 `side_target`

指本轮允许自然顺带带出的字段。可以没有，但不能抢主线。

### 4.7 兜底字段 `forced_cover_target`

指平时不抢主线，但在流程被阻塞时临时升级为必须覆盖一次的字段。

## 5. 拟人化的统一定义

本项目后续凡是讨论“提高拟人化程度”，统一按以下口径理解：

- AI 要先像是在听人说话。
- AI 要先接住用户刚表达的重点，而不是立刻切字段。
- AI 要像真人一样顺着用户当前这句话自然往下聊。
- 拟人化的核心标准是“听懂了，并且顺着接上了”。
- 单纯增加语气词、口头禅、表情、温柔措辞，不等于拟人化提升。
- 如果回复只是取字段、换字段、推进流程，即使语气柔和，也不算高拟人化。

评审时优先检查：

- 有没有接住用户刚说的重点
- 有没有顺着当前话题自然推进
- 有没有机械切字段、像问卷
- 有没有只是在取信息，而不是在对话

## 6. 字段分层

### 6.1 核心字段

- `sex`
- `age`
- `education`
- `occupation`
- `location`

### 6.2 中等字段

- `marital_status`
- `partner_requirement`
- `monthly_income`

### 6.3 联系方式字段

- `phone`
- `wechat`

注意：

- 联系方式不参与核心/中等字段覆盖完成判断。
- 身高、姓名、体重等低优字段仍只做被动提取，不主动追问。

## 7. 字段收集总原则

### 7.1 主线原则

- 核心字段是主线。
- 中等字段继续保留穿插问、自然结合问的产品要求。
- 联系方式明显后置，只有上游 gate 全部满足才允许进入。

### 7.2 每轮调度原则

- 每轮只允许一个 `main_target`。
- 每轮最多一个 `side_target`。
- 已收集字段不再主动重复问。
- 当前轮如果用户在提问、表达顾虑、投诉，则先答疑，不推进主目标。

### 7.3 交互原则

- 能承接就先承接，再推进。
- 能自然带出就自然带出，不做表单式连珠炮。
- 能轻问就不重问。
- 能顺带就不硬切。

### 7.4 核心字段顺序原则

核心字段仍然有主骨架，但不要求永远固定死序。

稳定要求：

- `sex` 仍然优先，通常作为最前面的核心字段。
- `age / location / education / occupation` 仍然属于核心主线。
- 不允许在核心字段明显未完成时，直接跳去中等字段或联系方式。

本版本新增规则：

- `age / location / education / occupation` 允许“受控扰动”式轻微换位。
- 这里的“受控扰动”不是完全随机，而是在有限候选顺序里做稳定选择。
- 目标是降低表单感，让对话更像顺着聊，而不是每次都固定成同一条采集路径。

因此，系统允许出现下面这类差异：

- 有的会话在 `sex` 后先问 `age`
- 有的会话在 `sex` 后先问 `location`
- 有的会话在 `sex` 后先问 `education`

但以下边界不变：

- `sex` 不应该长期被拖到很后面
- 未完成核心字段时，不能因为顺序变化而越过 Coverage Gate
- 顺序变化不改变“核心字段成功或问满 2 次算覆盖”的规则
- 顺序变化不改变联系方式进入条件

### 7.5 首轮分流原则

首轮不再统一按“直接开始问核心字段”处理，而是先判断用户首句属于哪一类入口。

当前统一分成 7 类：

1. 纯打招呼 / 试探在线
2. 首轮疑似错字 / 乱码 / 无法稳定理解
3. 明确表达求偶意图
4. 首轮主动提供资料
5. 首轮先问 FAQ / 可信度 / 收费 / 门店
6. 边界 / 拒绝型开场
7. 混合型首轮

具体口径如下：

- 纯打招呼：
  - 先建立连接，不直接采集资料
  - 轻问来意，确认用户是想找对象还是先了解情况
- 首轮疑似错字 / 乱码 / 无法稳定理解：
  - 进入 `opening_clarify`
  - 先轻量承认“这句没完全看懂/没太接住”
  - 再把对话拉回低压来意确认，如“想找对象 / 先了解下”
  - 不允许这一轮直接切 `sex / age / location` 等字段采集
- 明确表达求偶意图：
  - 不重复确认“是不是要找对象”
  - 直接承接后进入主线资料收集
- 首轮主动提供资料：
  - 先接住并入档用户已给的信息
  - 不回到机械固定顺序
  - 从相邻字段继续推进
- FAQ / 可信度 / 收费 / 门店：
  - 本轮先答疑，不采集资料
  - 下一轮再视用户态度回主线
- 边界 / 拒绝型开场：
  - 先接住边界
  - 不争辩，不立刻追问
  - 轻量降压后再看是否继续
- 混合型首轮：
  - 先识别主问题
  - FAQ / 顾虑优先答
  - 已给资料同步入档
  - 下一步按主线或相邻字段继续

混合型首轮的优先级建议：

1. 风险 / 顾虑
2. 明确提问
3. 明确求偶意图
4. 已给资料
5. 纯打招呼

### 7.6 开场连接型消息原则

本项目里，“打招呼”不再只理解为单个关键词，而是统一归入 `opening_connective`。

`opening_connective` 至少包含 4 类：

1. 普通打招呼
2. 连接试探
3. 组合型打招呼
4. 轻咨询开场

典型示例：

- 普通打招呼：
  - `你好`
  - `您好`
  - `哈喽`
  - `嗨`
  - `hi`
  - `hello`
- 连接试探：
  - `在吗`
  - `在不在`
  - `有人吗`
  - `有人在吗`
  - `方便聊吗`
  - `有空吗`
  - `可以聊吗`
- 组合型打招呼：
  - `你好，在吗`
  - `你好呀，在吗`
  - `hi，在吗`
  - `你好还在吗`
  - `在吗在吗`
  - `hello你好`
- 轻咨询开场：
  - `想了解下`
  - `想了解一下`
  - `看看情况`
  - `先咨询下`
  - `想问一下`

统一处理规则：

- 只要首轮整体仍是在建立连接，而不是明确求偶意图、FAQ、主动给资料或边界表达，就进入 `opening_probe`
- `opening_probe` 的回复必须先连接，再探测来意
- 不允许因为是组合句、重复句或中英混合，就误掉回字段采集

禁止行为：

- 用户说 `你好，在吗` 时直接问 `sex`
- 用户说 `hi` 时直接切核心字段
- 用户说 `想了解下` 时直接开始采集资料
- 用户首轮输入明显无法稳定理解时，禁止从“没看懂”直接跳到 `sex / age` 等字段问题

### 7.6.1 `opening_clarify` 原则

`opening_clarify` 用于首轮疑似错字、乱码、打字异常或无法稳定理解的输入。

统一范式：

1. 先轻澄清
2. 再回到开场分流
3. 不直接采字段

可接受的话术特征：

- 先承认“我这句有点没看懂 / 没太接住 / 没看明白 / 没反应过来”
- 再轻量确认用户来意，如“你是想找对象，还是先了解下呀？”
- 允许多变体，不固定一句模板

禁止行为：

- 先说“是不是打错字了”再直接追问 `sex`
- 用澄清当跳板，下一句立刻切 `age / location / education`
- 把 `opening_clarify` 写成客服式纠错公告

### 7.7 时间型打招呼校正原则

时间型打招呼属于 `opening_connective` 的特殊子类，必须结合系统当前真实时间做轻校正。

支持范围至少包括：

- `早上好`
- `早安`
- `上午好`
- `下午好`
- `晚上好`
- `晚安`
- `早啊`
- `晚上好在吗`

处理规则：

1. 先识别为 `opening_connective`
2. 若命中时间型问候词，再与系统当前真实时间段做比对
3. 若时间一致，正常回复
4. 若时间不一致，轻纠正后再回到开场连接分流

校正要求：

- 不能被用户输入的时间词带偏
- 不能机械复读用户的错误时间问候
- 纠正语气要轻，不要显得刻意或挑错
- 纠正后仍要继续探测用户来意

例如：

- 用户早上说 `晚上好`
  - 不应回复 `晚上好呀`
  - 应类似回复：
    - `哈哈，现在还是早上呢。你这边是想找对象，还是先了解下呀？`
- 用户下午说 `早安`
  - 不应回复 `早安`
  - 应类似回复：
    - `现在已经下午啦。你这边是想找对象，还是先看看情况呀？`

组合型时间问候同样适用：

- `晚上好在吗`
- `早安，你在吗`
- `下午好哈喽`

它们都不应掉回字段采集，而是应先完成时间校正，再继续 `opening_probe`

### 7.8 中等字段并问原则

中等字段默认不单独占轮，优先作为 `side_target` 吸附在语义相邻的核心字段后面，以减少总轮次和流程感。

推荐搭配：

- `occupation + monthly_income`
- `location + partner_requirement`
- `marital_status + partner_requirement`
- `education + occupation`
- `location + occupation`

规则说明：

- 中等字段平时弱化存在感，不抢主线
- 优先跟在语义相邻的核心字段后面自然带出
- 只有当中等字段成为 Coverage 的唯一阻塞项时，才允许单独升级为兜底目标

补充口径：

- 当用户首轮已经给出 `location + occupation` 时，下一步优先补低压核心字段，如 `age` 或 `education`
- `monthly_income` 在这类场景下更适合作为顺带问题，不默认升级为主问题

### 7.9 最新字段邻近优先原则

从本版本开始，字段调度不只看“全局还缺什么”，还要看“用户刚刚这句重点给了什么”。

统一要求：

- 用户刚主动给出的字段，优先作为下一问的局部路由依据
- 下一问应优先从这个字段的语义邻近字段里选，而不是马上回到全局固定顺序
- 这条规则适用于首轮主动给资料，也适用于后续轮次中的短答补充

推荐邻近关系：

- 用户刚给出 `location`：
  - 优先下一问 `occupation`
  - 其次 `education`
  - 再其次 `age`
- 用户刚给出 `occupation`：
  - 优先下一问 `education`
  - 其次 `age`
  - `monthly_income` 更适合作为顺带问题，不默认单独主问
- 用户刚给出 `age`：
  - 优先下一问 `location`
  - 其次 `education`
  - 再其次 `occupation`
- 用户刚给出 `education`：
  - 优先下一问 `occupation`
  - 其次 `location`
- 用户刚给出 `location + occupation`：
  - 优先补低压核心字段，如 `age` 或 `education`
  - 不默认直接主问 `monthly_income`

示例口径：

- 用户说：`男的呢，在深圳`
  - 更顺的下一步应优先问工作，而不是立刻回去问年龄
- 用户说：`90后，深圳，做IT`
  - 更顺的下一步应优先补 `education / marital_status` 等缺失字段，而不是回头重问城市或工作

### 7.10 明确求偶意图时的开放自述入口

当用户已经明确表达“想找对象”，但还没有提供任何资料时，系统不必每次都立刻进入硬字段提问。

允许策略：

- 先承接用户的求偶意图
- 在一部分轮次里，给用户一个开放自述入口
- 用户如果愿意主动介绍自己，就顺着他的自述抽取字段并继续推进

推荐口径：

- `好呀，那我先简单了解下你。你也可以先简单说说自己，我顺着了解会更自然一点。`
- `行呀，你要不先简单介绍下自己，我顺着了解会更顺一点；或者我先问你一个小问题也行。`

边界要求：

- 这不是每轮默认动作，只在用户明确表达求偶意图、且当前没有 FAQ / 边界 / 顾虑阻塞时使用
- 开放自述入口后，下一步仍要回到主线资料收集
- 不能因为开放自述而放弃核心字段收集

产品收益：

- 给用户更多主动权，降低“被盘问”感
- 更容易拿到系统平时不主动问的被动字段，如称呼、身高、体重
- 更容易让用户一次性说出多个核心字段，从而让后续问题更自然地顺着聊

## 8. 四个 Gate

## 8.1 Coverage Gate

Coverage Gate 只回答一个问题：

- 该问的字段轮次，走完没有

核心字段覆盖完成条件：

```python
core_covered = collected or ask_count >= 2
```

中等字段覆盖完成条件：

```python
medium_covered = collected or ask_count >= 1
```

Coverage Gate 通过条件：

```python
coverage_passed = all_core_covered and all_medium_covered
```

这里的关键不是公式本身，而是 `ask_count` 的语义：

- `ask_count` 不再等于“AI 提过几次”
- `ask_count` 表示“有效覆盖尝试次数”

只有在一次字段推进真正成立时，才计入 `ask_count`。

只要 `coverage_passed=False`，就不能进入联系方式。

## 8.2 Profile Sufficiency Gate

Profile Sufficiency Gate 只回答一个问题：

- 虽然该问的都问过了，但画像会不会太空，不适合切联系方式

规则：

```python
profile_sufficient = core_success_count >= 3
```

只统计：

- `sex`
- `age`
- `education`
- `occupation`
- `location`

注意：

- `profile_sufficient` 不是提前放行条件
- 它只能在 `coverage_passed=True` 后再生效

## 8.3 Turn Quality Gate

Turn Quality Gate 只回答一个问题：

- 当前这一轮，适不适合切联系方式

以下场景通常不适合切联系方式：

- 用户在提问题
- 用户在表达顾虑
- 用户在投诉
- 当前轮本来就该轻承接
- repair mode 修复中
- 当前轮是边界收口轮

输出：

```python
turn_quality_passed: bool
```

## 8.4 Cost Control Gate

Cost Control Gate 只回答一个问题：

- 还值不值得继续高成本推进

输出投入模式：

- `full`
- `compact`
- `light`
- `close`

含义：

- `full`：正常推进
- `compact`：压缩推进
- `light`：轻答，不主动推进
- `close`：停止主流程，礼貌收口

当前版本建议使用这些计数器：

- `non_cooperation_turns`
- `off_topic_turns`
- `open_profile_attempts`
- `session_token_spent`（如已有）

建议阈值：

- 连续不配合 >= 3：转 `light`
- 连续跑题 >= 3：转 `light`
- 开放式补画像失败 >= 2：转 `light`
- token >= 20000：转 `compact`
- token >= 35000：转 `light` 或 `close`

## 9. 字段级结果判定

为了让 `ask_count` 语义稳定，当前目标字段每轮只判 4 类。

### 9.1 `answered_target`

含义：

- 用户答到了当前主目标字段

例子：

- AI：你现在在哪个城市？
- 用户：我在深圳

处理：

- 当前字段收集成功
- 当前字段不再追问

### 9.2 `answered_other_field_only`

含义：

- 用户没答当前主目标字段
- 但答了别的有效字段

例子：

- AI：你现在在哪个城市？
- 用户：我做 IT

处理：

- 更新答到的字段
- 当前目标字段不算完成
- 当前目标字段第一次不记失败
- 下一轮给一次补问机会

### 9.3 `evaded_target`

含义：

- 用户明确回避当前主目标字段
- 或连续两次都错位跳过当前主目标字段

例子：

- 用户：这个先不说
- 或连续两轮只答别的字段，不答当前目标

处理：

- 当前目标字段 `ask_count` 增加 1

### 9.4 `interrupted_by_concern`

含义：

- 用户没有接字段，而是提问题、表达顾虑、质疑、投诉

例子：

- “线下有门店吗”
- “你们是不是骗子”
- “为什么要问这个信息”

处理：

- 当前字段 `ask_count` 不增加
- 本轮先答疑
- 下一轮恢复原目标

## 10. Coverage 只消费哪两类结果

Coverage 只消费：

- `answered_target`
- `evaded_target`

Coverage 不消费：

- `answered_other_field_only`
- `interrupted_by_concern`

原因：

- `answered_other_field_only` 说明用户只是答错位，不代表当前目标字段已经被问过并完成覆盖
- `interrupted_by_concern` 说明这一轮被用户疑问打断，不代表字段推进失败

## 11. 用户疑问优先机制

当 AI 正在推进核心字段或中等字段时，如果用户提问、质疑、表达顾虑或投诉，则：

- 本轮先答疑
- 本轮不推进字段
- 本轮不推进联系方式
- 当前字段不消耗 `ask_count`
- 保存：
  - `resume_profile_mode`
  - `resume_profile_target`
  - `last_user_concern_type`

下一轮如果用户不再继续追问，就优先恢复原目标。

恢复规则采用最简实现：

- 保存一次
- 恢复一次
- 恢复后立即清空

不引入多轮有效期。

## 12. 错位回答规则

如果用户没有回答当前目标字段，而是回答了别的字段：

第一次错位：

- 视为 `answered_other_field_only`
- 更新用户答到的字段
- 当前目标字段 `ask_count` 不增加
- 下一轮补问当前目标字段一次

连续第二次错位：

- 视为 `evaded_target`
- 当前目标字段 `ask_count` 增加 1

因此：

- 第一次答错字段，不立刻算拒绝
- 连续错位，才算一次有效未覆盖尝试

## 13. 双问题自然提问保留，但后台必须有主次

婚况、择偶要求、月薪继续保留当前产品设计：

- 穿插问
- 自然结合其他字段问
- 不改单问硬问

但后台必须维护：

- 一个 `main_target`
- 一个可选 `side_target`

如果用户只回答了 `side_target`：

- 更新 `side_target`
- `main_target` 仍未完成
- 下一轮补 `main_target`

## 14. `partner_requirement` 规则

保留现有原则：

- 平时是 `side_target`
- 不是主线硬问

增加兜底规则：

如果：

- 核心字段都已覆盖
- 联系方式还不能进入
- 未覆盖项只剩中等字段
- 特别只剩 `partner_requirement`

则允许：

- `partner_requirement` 升级成 `forced_cover_target`

如果它被用户疑问打断：

- 不消耗那一次覆盖机会
- 下一轮恢复继续问

## 15. Coverage 通过但画像不足时

当：

- `coverage_passed=True`
- `profile_sufficient=False`

则：

- 不进入联系方式
- 不回退到机械逐字段流程
- 进入 `open_profile_repair`
- 最多尝试 1 到 2 次

如果仍然不足：

- 进入 `low_pressure_chat`

当前版本不记录开放式补画像的目标字段，只保留轻量实现。

## 16. 联系方式进入条件

只有同时满足：

```python
can_enter_contact = (
    coverage_passed
    and profile_sufficient
    and turn_quality_passed
    and engagement_mode in {"full", "compact"}
)
```

才允许进入联系方式。

## 17. 联系方式流冻结规则

一旦联系方式流开始，主资料流冻结。

判定联系方式流已开始的条件：

- `phone_ask_count > 0`
- 或 `wechat_ask_count > 0`
- 或 `phone_collected = True`
- 或 `wechat_collected = True`
- 或 `rejected_phone = True`
- 或 `rejected_wechat = True`

只要满足任一，就认为已经进入或处于联系方式流。

此时：

- 不再主动推进核心字段
- 不再主动推进中等字段
- 不再重新选择资料类 `main_target`
- 不再触发 `forced_cover_target`
- `side_target = None`
- 只继续当前联系方式流程
- 如果用户主动补资料，只做被动提取，不主动追问

## 18. “无有效推进”的统一定义

新增一个轻量布尔规则：

- `made_effective_progress`

它只回答一个问题：

- 这轮有没有让主流程往前走半步以上

判定为 `True` 的情况，满足任一即可：

1. 收到了当前 `main_target`
2. 收到了其他核心/中等有效字段
3. 联系方式流有实质推进
4. 用户顾虑被成功处理，并允许恢复主流程

判定为 `False` 的情况：

1. 纯 FAQ 循环
2. 纯质疑/顾虑循环，且没有缓和
3. 纯寒暄、确认词、敷衍词
4. 连续错位回答，没有命中当前目标，也没有新增关键字段
5. 本轮既没字段推进，也没联系方式推进，也没解除用户顾虑

这条规则只用于：

- 更新 `non_cooperation_turns`
- 更新 `off_topic_turns`
- 辅助 `Cost Control Gate`

不单独做成新 Gate。

## 19. 决策顺序

每轮严格按下面顺序：

1. 先算 `Coverage Gate`
2. 再算 `Profile Sufficiency Gate`
3. 再算 `Turn Quality Gate`
4. 再算 `Cost Control Gate`
5. 如果用户疑问优先，则本轮先答疑并保存 `resume_target`
6. 如果联系方式流已开始，则冻结主资料流，只走联系方式
7. 基于结果决定 `next_mode`
8. 再决定本轮 `main_target / side_target / forced_cover_target / allow_contact_push`

## 20. `next_mode` 规则

```python
if has_ongoing_contact_flow(profile):
    next_mode = "contact_flow"
elif not coverage_passed:
    if unresolved_core_fields:
        next_mode = "collect_core"
    else:
        next_mode = "collect_medium"
elif not profile_sufficient:
    if open_profile_attempts < 2 and engagement_mode in {"full", "compact"}:
        next_mode = "open_profile_repair"
    else:
        next_mode = "low_pressure_chat"
elif not turn_quality_passed:
    next_mode = "contact_hold"
elif engagement_mode in {"light", "close"}:
    next_mode = "low_pressure_chat" if engagement_mode == "light" else "terminate_conversion"
else:
    next_mode = "contact_flow"
```

## 21. 下一步目标生成规则

如果当前不能进联系方式，并且又不在联系方式流中，就必须保证有下一步目标：

1. 先找未覆盖核心字段
2. 如果核心都覆盖了，再找未覆盖中等字段
3. 如果只剩 `partner_requirement`，允许它成为 `forced_cover_target`
4. 如果 `coverage_passed=True` 但画像不足，进入 `open_profile_repair`
5. 只有真正无事可做时，才允许轻收尾

也就是说：

- `ask_field=None` 不能裸跑给模型
- 一旦进入联系方式流，则不再回头主动找资料字段目标

## 22. 对话承接规则

每次推进字段前，优先做承接，不要直接硬问。

承接顺序：

1. 承接用户情绪
2. 承接用户内容
3. 给一句轻反馈
4. 再推进主目标字段

示例逻辑：

- 用户积极回答：轻反馈后继续推进
- 用户犹豫：先安抚，再降低问题压力
- 用户开玩笑：可轻接一句，再回主线
- 用户敷衍：不要立刻压问，先换轻方式
- 用户防备：先解释用途，再决定是否继续问

## 23. 转场规则

从一个字段切到另一个字段时，必须经过转场。

标准转场结构：

`承接上一句 → 反馈/认可 → 进入下一字段`

禁止：

- 刚问完职业，下一句直接问收入
- 刚问完年龄，下一句直接问婚况且无过渡

### 23.1 禁止开场白的执行口径

“禁止开场白”只表示：

- 禁止重复系统欢迎语
- 禁止重复自我介绍型固定开场

不表示：

- 禁止短承接
- 禁止一句轻反馈后再推进字段

执行口径：

- 非首轮：禁止重复欢迎语，但允许 1 句承接 + 1 个轻问题
- 首轮纯问候：必须先承接，再推进

## 24. 首轮体验原则

首轮用户体验优先级：

`接住用户 > 建立信任 > 给用户选择感 > 再推进字段`

首轮明确要求：

- 用户第一句是纯问候时，必须先自然承接，不得直接抛字段问题
- 不允许因为已有某个字段默认值就跳过问候承接
- 首轮可推进字段，但必须是“承接后轻推进”

## 25. 非收集型互动规则

为了更像真人，允许少量非收集型互动。

规则：

- 每收集 2 到 3 个有效字段，可插入 1 轮轻互动
- 轻互动只做短反馈，不长聊
- 下一轮必须回到主线

可做：

- 简短认可
- 轻微共情
- 对择偶表达做一句自然反馈

不可做：

- 连续两轮不收集
- 输出大段建议
- 变成陪聊

## 26. 用户控制权规则

首轮或关键转场轮，允许给用户一个轻量选择：

- “我先快速了解你两三点”
- “你先说你最在意的”

规则：

- 仅提供 2 个短选项，不做复杂分支问卷
- 选项必须口语化、低压力
- 用户未选择时，默认走“先听用户说，再轻推进”

## 27. 用户类型适配

| 用户类型 | 特征 | 对应策略 |
|---|---|---|
| 配合型 | 回答直接，信息量高 | 推进稍快，允许 1主 + 1顺带 |
| 保守型 | 回答短，对敏感问题回避 | 多解释、少压迫、少追问 |
| 敷衍型 | “嗯”“还行”“再说吧”较多 | 放慢推进，更多被动提取 |
| 话题型 | 愿意展开讲要求、生活、经历 | 先顺着聊，再从中提取字段 |

## 28. 记忆回用规则

用户已经说过的信息，后续回复里要自然回用。

规则：

- 回用要短，不要像复读资料
- 回用的目的是让用户感到“被听见了”

允许的回用：

- 地区
- 职业
- 择偶要求
- 已表达的偏好
- 已表达的顾虑

禁止：

- 大段重复用户资料

### 28.1 上下文承接硬约束

“记忆回用”不能只停留在提示词层，必须进入主流程决策。

系统每轮不只判断“下一步问什么”，还必须判断“这一轮先接什么”。

统一要求：

1. 先识别当前轮主落点
2. 再决定下一步动作
3. 回复必须先承接当前轮主落点，再推进主线或支线动作

当前轮主落点至少包括：

- `work_busy`
  - 例如：`我工作比较忙`
- `location_reuse`
  - 例如：`那边有什么好的相亲资源吗`
- `preference_reuse`
  - 例如：`有什么推荐吗`
- `faq_followup`
  - 例如：`你们怎么匹配`、`为什么要留电话`
- `boundary_pause`
  - 例如：`这个我不太方便说`
- `topic_shift`
  - 例如：`先不聊资料`
- `profile_partial_with_boundary`
  - 例如：`本科，不过这个先不太方便说`

执行口径：

- 当前轮命中主落点后，本轮回复必须先接住该落点
- 不能跳过承接，直接切到字段采集或联系方式推进
- FAQ 轮先答 FAQ，不得借答疑顺手要电话/微信
- `boundary_pause` / `topic_shift` / `profile_partial_with_boundary` 轮优先降压，不直接追字段
- `work_busy` / `location_reuse` / `preference_reuse` 轮，回复开头必须体现用户刚刚说的工作、城市、偏好等语义

这条规则是“动作约束”，不是“固定句式约束”：

- 固定的是：先承接，再推进
- 不固定的是：具体用哪一句话

禁止实现方式：

- 把 `work_busy` 固定成唯一一句模板
- 把 `location_reuse` 固定成唯一一句模板
- 把“承接上下文”实现成机械资料复读
- 只靠提示词提醒“先承接”，不做决策约束和交付校验

允许实现方式：

- 决策层输出 `followup_topic / context_ack_required / context_ack_type`
- 表达层按语义槽位生成多变体承接
- 交付前校验“是否真的接住了当前轮主落点”

### 28.2 非固定话术原则

上下文承接必须避免退化成固定模板系统。

统一要求：

- 固定策略结构，不固定具体句面
- 可以有多变体表达，但不能长期复读同一句
- 同一个 `context_ack_type` 允许不同句式、不同口语词、不同长度
- 重点是语义命中，而不是模板命中

例如 `work_busy`：

- 可接受：
  - `工作忙我能理解。`
  - `平时工作节奏比较满是吧。`
  - `做这类工作忙起来确实挺正常。`
- 不可接受：
  - 永远固定输出同一句

例如 `preference_reuse`：

- 可接受：
  - `你会更看重成熟稳重这一类，对吧。`
  - `成熟稳重这个点你是比较在意的。`
  - `你更偏向相处稳一点的类型。`
- 不可接受：
  - 每次都机械复读用户原话

### 28.3 交付前校验

“接住上下文”不能只靠生成模型自觉，必须在最终交付前做校验。

统一要求：

- 如果当前轮标记为 `context_ack_required=True`
- 但最终回复没有体现对应主落点语义
- 却直接进入字段追问、联系方式推进或空泛收口
- 则判定为 `context_drop`

`context_drop` 是需要被拦截并重写的交付错误，不是可接受的话术波动。

## 29. FAQ 与业务边界统一口径

以下 FAQ 场景统一按“先解释，再保持边界”处理：

- 收费
- 门店
- 怎么匹配
- 为什么要留电话/微信
- 能不能直接加对方
- 能不能先看照片
- 多久能安排 / 多久能找到
- 平台靠不靠谱 / 安不安全

统一要求：

- 可以解释，但不要讲成承诺
- 可以自然，但不要讲成营销
- FAQ 轮不要顺手切回资料收集

### 29.1 推荐表达方向

联系方式用途：

- 推荐说法：后面沟通更方便、后续确认会更顺一点
- 禁止说法：有合适的人选时第一时间联系你、给你发资料

门店/线下：

- 推荐说法：有线下门店，具体怎么安排以后续沟通为准
- 禁止说法：匹配后给你发具体定位、安排线下见面

照片/资料：

- 推荐说法：这类内容不是当前阶段直接发的，会先看沟通和隐私边界
- 禁止说法：双方合适后互换照片、先把资料发你

流程/匹配：

- 推荐说法：先了解基本情况和偏好，后面再继续沟通
- 禁止说法：马上安排、马上出结果、明确时效承诺

## 30. 低信息回复规则

用户若只回以下低信息表达：

- 好
- 好的
- 嗯
- 行
- 可以
- 回头再说

执行口径：

- 不要误判为用户已提供联系方式
- 不要机械复读上一轮问题
- 电话推进过一次后，低信息确认可自然切到微信方案
- 双渠道都推进过后，低信息确认应暂停联系方式推进
- “回头再说”优先按边界/暂缓处理，不再继续硬推联系方式

## 34. 技术落地建议

建议拆成 4 层：

| 模块 | 职责 |
|---|---|
| 字段调度层 | 决定当前 `main_target`、`side_target`、`forced_cover_target` |
| 提取层 | 从用户消息中提取全部字段 |
| 表达层 | 负责承接、转场、问法层级、FAQ 回答边界 |
| 联系方式层 | 继续使用现有独立逻辑 |

最小实现顺序：

1. 先做字段优先级与 Gate 决策
2. 再做中等字段穿插与 `partner_requirement` 兜底
3. 再做用户疑问优先与恢复
4. 再做联系方式冻结
5. 最后做“无有效推进”并接入成本控制

顺序相关新增检查：

- 不要再把 `age -> location -> education -> occupation` 当成唯一合法固定顺序。
- 自动化测试应验证“当前仍在核心字段集合中推进”，而不是强依赖某一个唯一字段顺序。
- 当 `sex` 已完成后，`age / location / education / occupation` 任一被选为下一核心主目标，都可以视为策略允许范围。
- 但测试仍要卡住以下越界行为：
  - 核心字段未覆盖时直接切中等字段
  - 核心字段未覆盖时直接切联系方式
  - 已完成字段被无意义重复主动追问

## 36. 当前实现口径

当前项目中，这套方案已经接入主流程，后续实现和修正都应继续遵守本文档口径：

- 4 Gate 是唯一主判断框架
- 字段推进统一按“有效覆盖尝试次数”而不是“AI 提过几次”
- 答疑轮不消耗当前字段覆盖次数
- 第一次错位回答不立刻记为拒绝
- 联系方式流一旦开始，主资料流冻结
- `made_effective_progress` 统一驱动运行态计数与降级逻辑

## 37. 最终产品规则，压缩版

1. 核心字段完成标准是“收集成功或有效覆盖尝试满 2 次”。
2. 中等字段完成标准是“收集成功或有效覆盖尝试满 1 次”。
3. 联系方式不参与核心/中等字段覆盖完成判断。
4. 所有核心和中等字段都完成覆盖后，才有资格进入联系方式判断。
5. 即使覆盖完成，核心成功数不足 3，也不进入联系方式，而先做开放式补画像。
6. `partner_requirement` 平时穿插问，但成为唯一阻塞项时可临时升级为兜底目标。
7. 用户提问、质疑或顾虑时，本轮先答疑，不消耗当前字段覆盖次数，下一轮恢复原目标。
8. 用户第一次答错字段不算拒绝，连续错位才算一次有效未覆盖尝试。
9. 一旦联系方式流开始，主资料流冻结，只继续处理联系方式；资料只做被动提取，不再主动追问。
10. 若本轮既未推进字段、未推进联系方式、也未消除用户顾虑，则判定为“无有效推进”，用于驱动轻答或收口。
